The mechanism is one comparison in `askwell.ask._run_generation`, right after `retrieve()` returns and before anything downstream runs: the best of `[candidate_score(c) for c in candidates]` against `result.threshold`. Below it (or no candidates at all), `compose()` and the model are never called — `citation_rows` stays empty, which is exactly what already makes `summarize_turn` (`M1-CONV-BE-177`) treat the turn as abstained, `source_count = NULL`. Above it, nothing changes from before this ticket.

**The real work was finding a score actually comparable to the threshold.** `Settings.retrieval_score_threshold` is `[0, 1]`-bounded with a `0.65` default written against a plain example score (`docs/architecture.md` §7.1's "the right passage scored 0.61"). None of `Candidate`'s four scores are that on their own: the fused RRF score tops out near `1/61 ≈ 0.016` and exists to order candidates, not to report confidence, and a reranked candidate's own score is a raw cross-encoder logit — `InferenceClient.rerank`'s own docstring (`M1-ASK-RET-036`) says plainly it is unbounded and "the caller is not invited to threshold on the number itself." New `askwell.retrieve.candidate_score` resolves this with a sigmoid over the logit when reranking ran (the transform a cross-encoder is trained to be read through), falling back to the real dense cosine similarity — already `[0, 1]` — for a candidate reranking never touched, and lexical `ts_rank` as the last resort. Full reasoning, including what was rejected, in `docs/decisions.md`.

**The source-scoped "still indexing" edge case needed its own reason, not just its own copy.** `askwell.ask._abstain_reason` distinguishes `empty_corpus`, `source_indexing` and `below_threshold`: for a scoped question it reuses `askwell.ingest.coverage` (the library's own source-status query) rather than checking `documents.status` directly, because a document can have an embedded, chunk-searchable candidate before its own `status` column reaches `ready` — conflating the two would call a partially-searchable source empty. The corpus-wide empty check queries chunk existence joined to live documents instead, matching exactly what `askwell.retrieve`'s own SQL filters on (`deleted_at`/`superseded_by`, never `status`).

**`audit_interactions` gained `abstained` and `threshold`** so C5's own audit requirement (`docs/audit-log.md` §7, "abstentions" as a named thing the interaction log records) is queryable directly rather than only inferable from `citation_count == 0`, which was already true but not indexed as the fact it is.

**Before that: `M1-ASK-API-038`** — server-sent answer streaming with named retrieval steps. `0.2.19`. Issue [#152](https://github.com/Rumeasiyan/askwell/issues/152).

`api/src/askwell/ask.py` is new: `POST /ask` resolves or opens a conversation, records the question, starts a background `_generate` task, and returns a `text/event-stream` response that tails it. `GET /ask/{message_id}/stream` reconnects to the same turn — live from memory while it exists, from `messages` once it has left memory (retired past `MAX_FINISHED`, or this process having restarted). `POST /ask/{message_id}/stop` sets a flag `_generate` checks between tokens; the stored answer is written with `trace.stopped_early = true` either way it ends early (stopped or failed). Four SSE event kinds, exactly as scoped: `step` (before retrieval, after it with the source count, before generation), `token`, `citation` (resolved from `[index]` matches against the model's own streamed text, mapped back to the candidate `compose()` gave that index), `done`. `InferenceClient.stream_generate` is new — llama.cpp's own SSE `/completion` response, parsed into `StreamChunk`s, raising the same `InferenceUnavailable`/`InferenceFailed` pair every other method raises, including mid-stream if the process dies after tokens were already sent.

**Generation does not live inside the HTTP request.** `asyncio.create_task` starts it from the `POST /ask` handler and nothing awaits or cancels it there; a dropped connection ends the *response generator* (`_tail`), never the task writing to the `_Turn` it was tailing. This is what makes "client disconnects, generation continues, answer is saved" true without a queue, a worker or a second process — the whole product is one machine, one user, and the event loop already running the request is the only concurrency primitive this needed.

**Reconnect replays a turn's own history in full**, rather than resuming exactly where a dropped connection left off — a deliberate departure from the ticket's stated "does not replay tokens already sent." Full reasoning, and the bug in the literal reading that motivated it, in `docs/decisions.md`, 2026-08-28.

What was wrong, found by testing the ticket's own example against the real running database rather than assuming the schema was already right: Postgres's default text search parser reads a hyphen immediately before a digit run as a *sign*, not a separator, so `to_tsvector('english', 'INV-2024-0917')` produced `'inv':1 '-2024':2 '-0917':3` — the minus sign baked into each numeric lexeme — and a query for just `0917`, the realistic case of someone remembering only part of a reference number, never matched. A new migration, `c7e2f814a5b3`, changes the generated column's expression to `to_tsvector('english', regexp_replace(coalesce(content, ''), '-', ' ', 'g'))` — hyphens become spaces before tokenising, so `INV-2024-0917` now indexes as three independent, signless lexemes, each matchable alone. Full reasoning, including the two alternatives rejected (a custom parser extension; a second normalised column) and the cost accepted (a genuine hyphenated English compound like `well-known` loses its compound lexeme, though both halves still index and match), in `docs/decisions.md`, 2026-08-28.

A generated column's expression cannot be altered in place, so the migration drops and re-adds `content_tsv` and its index rather than editing `a8208099ef38` — which had already run against a live database, making a second migration the only honest option.

**Before that: `M1-INDEX-ING-031`** — structure-aware chunking. `0.2.12`. Issue [#135](https://github.com/Rumeasiyan/askwell/issues/135).

`api/src/askwell/chunk.py` is a new pipeline stage, installed into `ingest.STAGES` in place of the `None` placeholder `M1-ADD-ING-025` left there. It reads `document_pages.text` exactly as the extractors already left it — Markdown-style `#` headings, `[TABLE]`/`[/TABLE]` markers with `|`-separated rows (`extract_docx`, `extract_pptx`), `-`/`1.` list items — rather than re-parsing bytes a second time, and writes `chunks.document_id`, `.ordinal`, `.page_from`/`.page_to`, `.heading` and `.content`; `.embedding` stays null for `M1-INDEX-ING-032`. A document now parks at `embed` instead of `chunk`.

Three structural rules, one guarantee:

- **A table never splits from its header.** A table under the hard maximum stays one fragment, header and rows together; a table over it is split by row with the header repeated on every part (`_split_table`).
- **A heading is metadata, not duplicated content.** Encountering a `#` line closes whatever chunk was open and becomes every following chunk's `heading` column until the next heading — never a repeated line burned into `content`.
- **Anchors merge freely except slides.** `page`, `heading` and `sheet_row` anchors merge across pages up to the target size, which is what turns a heading-free PDF into sentence-bounded chunks instead of one per page. `documents.anchor_kind = 'slide'` never merges two slides into one chunk — one slide is one chunk unless it alone needs splitting.
- **The hard maximum is guaranteed by construction.** `_enforce_max` is a final whitespace-boundary split applied to every finished chunk regardless of how it was built, so `No chunk may exceed the hard maximum` holds even against a pathological input (a single sentence with no punctuation for ten thousand characters) none of the structural logic anticipated.

Sizes (`CHUNK_TARGET_CHARS = 1600`, `CHUNK_HARD_MAX_CHARS = 2400`, `CHUNK_OVERLAP_CHARS = 200`) are plain module constants rather than `Settings` fields, deliberately — reasoning in `docs/decisions.md`, 2026-08-28.

**Before that: `M1-EXTRACT-ING-029`** — flag low-confidence OCR and surface it as needs attention. `0.2.10`. Issue [#128](https://github.com/Rumeasiyan/askwell/issues/128).

Every OCR'd page now carries a confidence figure — Tesseract's own mean word confidence, from a second `image_to_data` pass alongside the existing `image_to_string` recognition (`api/src/askwell/extract_ocr.py`). `extract_pdf.run` stores it two places: `document_pages.ocr_confidence` (new column, this ticket's migration) per page, and `documents.ocr_confidence` (already existed, unread until now) as their mean. **Before that: `M1-ADD-ING-021`** — Askwell can be told which folders it may read. `0.2.2`.

Indexing in place means Askwell reads the user's own directories, so it needs a route to them that is narrow and explicit. That route is now two things that must not be confused:

- **The registry** — `roots`, its own table, tombstoned on removal. It is the *permission*: `askwell.roots.covering()` is the check, and a path no row covers is never read. It resolves symlinks, because one link inside a nominated folder would otherwise stand in for the whole disk.
- **The mount** — `ASKWELL_ROOTS_MOUNT`, one host directory bind-mounted read-only into the API and worker **at the same absolute path it has on the host**. It is the *route*. Identity mounting is deliberate: `sources.root_path` holds host paths, and any other mount point would need host↔container translation everywhere a path is stored, shown or reopened.

Mount state is **probed on every read and never stored**. A stored value reports an unplugged USB drive as available an hour later, and nothing would ever correct it.

Four unreadable states, kept apart because they have four different fixes: `not_mounted` (a line in `.env` and bring the stack up again), `unavailable` (a drive or share not connected — **never** rendered as deleted or as moved), `unreadable` (permissions, or SELinux on the mount), `available`.

A folder outside the window is **registered anyway**, reporting what to set and that the stack must come up again. Everything else unreadable is refused at registration, because it is true now and will not fix itself; a missing mount is not.

Reachable at `GET /roots`, `POST /roots`, `GET /roots/covering`, `GET /roots/{id}/removal`, `DELETE /roots/{id}`, and in the interface under Settings → Folders Askwell may read. Registering and removing are decisions records. Full reasoning in `decisions.md`, 2026-08-27; the flow is specified in `ux/add-source.md` §7, which is new — no screen covered path registration before.

**Before that: [#89](https://github.com/Rumeasiyan/askwell/issues/89)** — inference is three processes. This blocked M1 retrieval and is now cleared.

```
generation  ready   Qwen3.5-4B-Q4_K_M.gguf
embedding   ready   bge-m3-FP16.gguf              1024 dimensions
reranking   ready   bge-reranker-v2-m3-FP16.gguf
```

Through the client, from inside the API container, over one socket:

```
generate: 8 tokens
embed:    2 vectors of 1024 dimensions
rerank:   "how much notice to end the lease?"
  -2.419  Either party may terminate on ninety days written notice.
  -7.846  The tenant shall pay rent monthly in advance.
 -11.028  The premises shall be used for office purposes only.
```

The reranker puts the right passage first by a wide margin, which is the signal retrieval needs. **The scores are raw logits, not probabilities** — negative and unbounded — so only their order means anything, and the client returns them sorted rather than inviting a threshold on the number.

**Why this was necessary rather than tidy.** Embeddings from the generation model came back at 2560 dimensions where `chunks.embedding` is `vector(1024)`. They would not have been merely poor for retrieval — the database would have refused the insert. And `--reranking` needs its own model and is mutually exclusive with generation.

Each role is supervised independently: one model missing does not stop the others, because a user with no reranker can still ask questions and reporting the assistant down for it would be false. Three supervisors share one state file, written under a lock — without it they read-modify-write over each other and a role's entry vanishes, which the API would read as that role never having reported.

Both models verified against the registry before their names were written down (C9): `bge-m3` is MIT with 36M downloads, `bge-reranker-v2-m3` is Apache-2.0 with 18M. Both ungated.

## The repositioning — read this before anything else

On **2026-08-10** the product was redefined. The previous documentation described a materially different product and much of it was wrong, not merely outdated.

| Was | Is |
| --- | --- |
| Sold to government ministries, hospitals, banks | Free download for one individual professional |
| Organisations, four roles, RBAC, seat tiers, LKR pricing | **Single user, single machine.** No roles, no tenancy, no licence |
| Quantum Plus product with a "Deployer" persona | Standalone venture by Suseenthiran Arulraj Rumeasiyan; users install it themselves |
| Air-gapped, no network calls, ever | Local by default; **online AI is an explicit per-conversation opt-in**, and it is the only revenue line |
| Documents + live database connections | Also **CSV and SQL dump import**, with a sandbox for dumps |
| Ingest silently | **Clarification loop and memory** — the differentiator |

## Notes for the next session

**Read these first — each cost real time to learn.**

- **A model name is never asserted from memory, including from a decision entry.** `docs/decisions.md`'s 2026-08-10 entry claimed Qwen3.5 was not a real release; it is, and that entry downgraded the generation model by a family version. It now carries a superseded banner, because newest-first ordering protects a person reading top-down and not a `grep` — and a `grep` is what an agent uses. Verify against the registry every time (`AGENTS.md` §4).
- **The build runner's failures have almost all been in the harness, not the agents.** Seven were fixed in one session and every one had the same shape: something reporting a failure the work did not have, or a success it had not earned — agents that could not run the toolchain, a gate row whose pass line was a substring of its failure line, model knobs declared and read by nothing, a killed queue leaving its agents alive, an orphaned runner editing the tree for seven hours, a bare `git pull` refusing a diverged branch, and a rejected ticket's work following the checkout onto `main`. When a ticket fails, suspect the machinery before the code.
- **An audit rejection is usually right.** Of the rejections in that session, every one named a real defect the six-row gate had passed: a merged-cell counter that could only ever report zero, an auto-retry that overwrote "wrong password" with "password protected", an acceptance criterion with no implementation, a stale ref dropping streamed tokens, `except AuditError` not catching the database failure it existed for, and follow-up padding that three tests asserted *as correct*. That last one is the pattern to fear: a test encoding the wrong requirement passes the gate and makes the defect look deliberate.
- **Prove a fix with a mutation.** Break the fix, run the suite, confirm the new test fails and nothing else does. It caught two tests this session that would otherwise have proved nothing — and once produced a hang rather than a failure, which turned out to be exactly the user-visible symptom.
