## Current phase

**M1 — It answers from my documents. In progress.** `0.2.15`. M0 complete, 21 of 21.

The repository is no longer documentation only. `api/` exists: an image, manifests, the application, and a test suite across forty-odd modules (the exact count is what `scripts/dev.sh test` prints — a number written down here goes stale within a ticket). The API starts, refuses bad configuration by name, and serves `GET /health` reporting five components separately. `podman compose up -d` brings up four services, the database carries the full v1 schema, and the interface loads at `http://127.0.0.1:8000`. `web/` builds to static assets and the API serves them — the `web` container is gone from the topology. Material can be handed to Askwell, refused by name, and — since `M1-ADD-BE-023` — recorded as sources and documents with content-hash duplicate detection. Since `M1-ADD-ING-025` those records go onto a durable queue that a worker drains in the background, with per-file progress streamed to the browser and a queue that survives a restart. Since `M1-EXTRACT-ING-026` a text-layer PDF is actually read: page text, page count and per-page usability land in Postgres. Since `M1-EXTRACT-ING-027` six more formats read for real — `.docx`, `.pptx`, `.xlsx`, `.txt`, `.md`, `.html` — each with its own page-equivalent anchor (`documents.anchor_kind`, `document_pages.anchor_label`). Since `M1-EXTRACT-ING-028` a scanned PDF with no text layer is read too — OCR with orientation detection runs inline inside `extract`, per page. Since `M1-EXTRACT-ING-029` that OCR pass also measures its own confidence, per page and per document, and a low-confidence document flags its source `needs attention` with a specific reason rather than indexing silently. Since `M1-EXTRACT-VAL-030` a document Askwell cannot even open is classified before any parser sees its bytes — missing from disk, unreadable, corrupt, or password-protected each read distinctly by file name — and a password-protected PDF prompts for its password (`POST /ingest/documents/{id}/password`) rather than exhausting its retries silently; the password is carried for one attempt only, in the job queue, never in Postgres or a log line. Since `M1-INDEX-ING-031` extracted text is actually chunked — a table never splits from its header, a heading is carried as metadata on every chunk beneath it, a heading-free run breaks at sentence boundaries, a slide is never merged with another slide. Since `M1-INDEX-ING-032` a chunked document is actually embedded — `embed` sends every un-embedded chunk to the native inference process in bounded batches, retries a failing batch with backoff, and a document reaches `ready` only once every one of its chunks has a vector. **The pipeline is complete for the first time**: `extract`, `chunk` and `embed` are all real, and a clean document now runs start to finish to `ready` with nothing named as still missing.

**`M1-INDEX-BE-034`** — supersede a changed document rather than duplicating it. `0.2.15`. Issue [#140](https://github.com/Rumeasiyan/askwell/issues/140).

`api/src/askwell/sources.py`'s `add` now recognises a third case beyond duplicate and new document: a file at a path that already holds a *live* document, whose content hash differs. It is offered, not decided for the caller — `Outcome.NEW_VERSION`, nothing recorded — until a second call answers via the new `version_decisions: dict[relative_path, "supersede" | "keep_both"]` on `POST /sources`. `"supersede"` inserts the new document at `version + 1` and sets the old row's `superseded_by` to it, in one transaction, plus a `document_superseded` decisions record naming both; `"keep_both"` inserts it as an ordinary independent document with no link — which the schema already permitted, since `uq_documents_live_source_id_sha256` is keyed on content, not path. The match is on exact `path`, so `clients/contract.pdf` and `archive/contract.pdf` stay unrelated; content-hash duplicate recognition (unchanged) runs first, so identical content under a new path is still a plain duplicate, never a version offer.

Repeated re-adding chains correctly rather than orphaning: the candidate lookup is always `superseded_by IS NULL`, so a second edit of the same path finds the version left live by the first supersession, not the original.

**Before that: `M1-INDEX-DB-033`** — full-text column population and index. `0.2.14`.

Turned out to be a bug fix, not new plumbing: `chunks.content_tsv` and its GIN index (`ix_chunks_content_tsv`) already existed and already auto-populated every write, since the v1 schema migration (`a8208099ef38`) made `content_tsv` a `GENERATED ALWAYS AS ... STORED` column — no trigger, no application write, nothing for this ticket to add there. What was wrong, found by testing the ticket's own example against the real running database rather than assuming the schema was already right: Postgres's default text search parser reads a hyphen immediately before a digit run as a *sign*, not a separator, so `to_tsvector('english', 'INV-2024-0917')` produced `'inv':1 '-2024':2 '-0917':3` — the minus sign baked into each numeric lexeme — and a query for just `0917`, the realistic case of someone remembering only part of a reference number, never matched. A new migration, `c7e2f814a5b3`, changes the generated column's expression to `to_tsvector('english', regexp_replace(coalesce(content, ''), '-', ' ', 'g'))` — hyphens become spaces before tokenising, so `INV-2024-0917` now indexes as three independent, signless lexemes, each matchable alone. Full reasoning, including the two alternatives rejected (a custom parser extension; a second normalised column) and the cost accepted (a genuine hyphenated English compound like `well-known` loses its compound lexeme, though both halves still index and match), in `docs/decisions.md`, 2026-08-28.

A generated column's expression cannot be altered in place, so the migration drops and re-adds `content_tsv` and its index rather than editing `a8208099ef38` — which had already run against a live database, making a second migration the only honest option.

**Before that: `M1-INDEX-ING-032`** — embedding batches with retry and visible failure. `0.2.13`.

`api/src/askwell/embed.py` is the pipeline's third and final declared stage, installed into `ingest.STAGES` in place of the `run=None` placeholder every prior ticket left there. For each un-embedded chunk of a document (`WHERE embedding IS NULL`, so a retried job never re-sends work already done), it batches content in groups of `ASKWELL_EMBEDDING_BATCH_SIZE` (default 16, a new `Settings` field — a machine-sizing knob like `ingest_concurrency`, not a retrieval-quality constant like `chunk.py`'s sizes) and calls `InferenceClient.embed`. A batch that fails retries up to three times with a short linear backoff (`embed._embed_batch`) before the whole document falls through to the pipeline's existing per-document retry and failure surface — nothing new needed there, `GET /ingest` and `POST /ingest/documents/{id}/retry` already render and act on any stage's failure by name.

Three things this ticket decided, in `docs/decisions.md`:

- **`StageFn` grew a fourth argument, `Settings`**, because `embed` is the first stage that needs configuration (the inference socket, the batch size) rather than only a file and a place to write. `extract.run` and `chunk.run` both take and ignore it. The prior ticket's decision log explicitly deferred this exact widening rather than avoiding it.
- **The embedding dimension is checked once, at worker startup** (`embed.check_dimension`, called from `askwell.worker.startup`), against `chunks.embedding`'s actual deployed width — read via `format_type(atttypid, atttypmod)` rather than assumed. A mismatch is the one case in `startup`'s broad "Postgres may not be up yet" exception handler that is deliberately *not* swallowed: it re-raises and crashes the worker, because a configuration/schema mismatch is a fact that will not fix itself on the next reconcile the way a slow database will.
- **An empty chunk is refused as a second line of defence** (`embed.EmptyChunk`) — `askwell.chunk` already guarantees this cannot happen, so this exists purely so a defect upstream surfaces as a named, retryable failure rather than a citation pointing at nothing.

**Before that: `M1-INDEX-ING-031`** — structure-aware chunking. `0.2.12`. Issue [#135](https://github.com/Rumeasiyan/askwell/issues/135).

`api/src/askwell/chunk.py` is a new pipeline stage, installed into `ingest.STAGES` in place of the `None` placeholder `M1-ADD-ING-025` left there. It reads `document_pages.text` exactly as the extractors already left it — Markdown-style `#` headings, `[TABLE]`/`[/TABLE]` markers with `|`-separated rows (`extract_docx`, `extract_pptx`), `-`/`1.` list items — rather than re-parsing bytes a second time, and writes `chunks.document_id`, `.ordinal`, `.page_from`/`.page_to`, `.heading` and `.content`; `.embedding` stays null for `M1-INDEX-ING-032`. A document now parks at `embed` instead of `chunk`.

Three structural rules, one guarantee:

- **A table never splits from its header.** A table under the hard maximum stays one fragment, header and rows together; a table over it is split by row with the header repeated on every part (`_split_table`).
- **A heading is metadata, not duplicated content.** Encountering a `#` line closes whatever chunk was open and becomes every following chunk's `heading` column until the next heading — never a repeated line burned into `content`.
- **Anchors merge freely except slides.** `page`, `heading` and `sheet_row` anchors merge across pages up to the target size, which is what turns a heading-free PDF into sentence-bounded chunks instead of one per page. `documents.anchor_kind = 'slide'` never merges two slides into one chunk — one slide is one chunk unless it alone needs splitting.
- **The hard maximum is guaranteed by construction.** `_enforce_max` is a final whitespace-boundary split applied to every finished chunk regardless of how it was built, so `No chunk may exceed the hard maximum` holds even against a pathological input (a single sentence with no punctuation for ten thousand characters) none of the structural logic anticipated.

Sizes (`CHUNK_TARGET_CHARS = 1600`, `CHUNK_HARD_MAX_CHARS = 2400`, `CHUNK_OVERLAP_CHARS = 200`) are plain module constants rather than `Settings` fields, deliberately — reasoning in `docs/decisions.md`, 2026-08-28.

**Before that: `M1-EXTRACT-VAL-030`** — extraction failure states: corrupt, encrypted, password-protected. `0.2.11`. Issue [#131](https://github.com/Rumeasiyan/askwell/issues/131), closed.

Extraction failure went from one grey `except Exception` catch-all to four named exceptions read where they belong. `extract_common.check_readable(work)` — called once, in `extract.run`'s dispatcher, ahead of every format's own parser — opens the file and turns `FileNotFoundError` into `MissingSource` and any other `OSError` into `UnreadableSource`, both naming the file and its recorded path; this is shared across every extractor because a file deleted between add and extraction is the same fact regardless of which library was about to read it. `extract_pdf.py` adds the PDF-specific split: pdfium's own `PdfiumError.err_code` distinguishes `FPDF_ERR_FORMAT`/`FPDF_ERR_UNKNOWN` (`CorruptDocument`) from `FPDF_ERR_PASSWORD`/`FPDF_ERR_SECURITY` (`PasswordProtected` if no password was supplied for this attempt, `WrongPassword` if one was and it did not work).

A password-protected PDF now has a way forward instead of a dead end. `POST /ingest/documents/{id}/password` resets a failed job to `queued` — reusing `retry`'s own reset, attempts forgiven — and dispatches it with a password. `Work` grew a fifth field, `password: str | None = None`, applied by `ingest.process` via `dataclasses.replace` after `_claim`, never read from or written to a database row: the password rides the `arq` job payload alongside `document_id`, the same transport every other job argument already uses, and is never named as a value to `structlog` (only *whether one was supplied* crosses into a log line, in `_classify_open_failure`). Full reasoning, including why a database row was considered and rejected, in `docs/decisions.md`, 2026-08-28.

**Before that: `M1-EXTRACT-ING-029`** — flag low-confidence OCR and surface it as needs attention. `0.2.10`. Issue [#128](https://github.com/Rumeasiyan/askwell/issues/128).

Every OCR'd page now carries a confidence figure — Tesseract's own mean word confidence, from a second `image_to_data` pass alongside the existing `image_to_string` recognition (`api/src/askwell/extract_ocr.py`). `extract_pdf.run` stores it two places: `document_pages.ocr_confidence` (new column, this ticket's migration) per page, and `documents.ocr_confidence` (already existed, unread until now) as their mean. A text-layer page or document carries neither — confidence is a fact about a page Tesseract was actually asked to read, and a document that never used OCR has nothing to be false about.

Below `ASKWELL_OCR_CONFIDENCE_THRESHOLD` (default `0.60`, `api/src/askwell/config.py`), a document is flagged. Flagging is never a failure and never touches `documents.status` — the document is exactly as indexed as any other. What changes is the *source*: `askwell.ingest.source_status` now takes a `flagged` count alongside `failed`, and returns `attention` the moment one exists, independent of `outstanding` — unlike a failure, a flag never retries and never waits for the rest of an import to finish. `sources.last_error` names both causes when both are true ("2 of 60 files could not be indexed. 1 file scanned poorly and may be hard to search."), and the `/ingest` snapshot grew a `flagged` list — mirroring the existing `failures` list — naming the specific pages that read worst per document, plus a local `documents_flagged` counter (C1: nothing transmitted). `web/lib/ingest.ts` and `add-screen.tsx` render it next to the existing failure list, with no retry control — there is nothing to click yet, only something to read (the re-scan clarification is `M3`, explicitly out of scope).

One decision worth reading in full in `docs/decisions.md`: the flagged count is deliberately **not** gated on `documents.status = 'ready'`, unlike every other `Coverage` figure. `chunk` and `embed` are not built yet, so today every document parks at `queued` once `extract` finishes — none ever reaches `ready`. Gating the flag the same way `ready`/`failed` are gated would have shipped something inert until two tickets this one does not depend on land.

The reranker puts the right passage first by a wide margin, which is the signal retrieval needs. **The scores are raw logits, not probabilities** — negative and unbounded — so only their order means anything, and the client returns them sorted rather than inviting a threshold on the number.

**Why this was necessary rather than tidy.** Embeddings from the generation model came back at 2560 dimensions where `chunks.embedding` is `vector(1024)`. They would not have been merely poor for retrieval — the database would have refused the insert. And `--reranking` needs its own model and is mutually exclusive with generation.

Each role is supervised independently: one model missing does not stop the others, because a user with no reranker can still ask questions and reporting the assistant down for it would be false. Three supervisors share one state file, written under a lock — without it they read-modify-write over each other and a role's entry vanishes, which the API would read as that role never having reported.

Both models verified against the registry before their names were written down (C9): `bge-m3` is MIT with 36M downloads, `bge-reranker-v2-m3` is Apache-2.0 with 18M. Both ungated.
