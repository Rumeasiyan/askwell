# Manual test — M6.5-WEB-BE-189, retrieval timestamps, stored with the turn

**Ticket:** `M6.5-WEB-BE-189` — a `web_citations` table, structurally distinct from `citations`,
that stores a used web result's domain, title, full URL, passage, and mandatory retrieval
timestamp, written in the same transaction as the turn, never updated afterward, and readable
back with no network access at all.

**Version under test:** `0.6.13`
**Time:** about 25 minutes. No native inference GPU/CPU tier matters — every step below either
goes through the real, running app with local inference only, or reads/writes the database
directly.

**What is being checked.** `api/src/askwell/db/models.py`'s `WebCitation`, the
`d3e6b1a94f02_web_citations` migration, and `api/src/askwell/websearch.py`'s
`WebCitationRecord`, `web_citation_record`, and `record_web_citations`.

**This is a backend-only ticket with no product surface yet, same shape as `M6.5-WEB-BE-185` and
`M6.5-WEB-BE-188`.** `record_web_citations` has exactly zero callers anywhere in
`api/src/askwell/api/` or `api/src/askwell/agent/` today — nothing in the answer path calls
`escalate_web_search` (`M6.5-WEB-FE-186`, the escalation offer, is unbuilt), so nothing in the
running app can ever produce a row in `web_citations`. `web/` has no rendering for one either
(`M6.5-WEB-FE-190`, separate ticket, out of scope here). Read "Known gaps" before reporting a
missing web citation as a defect. Part A proves the corpus and citation tables stay untouched
through ordinary use of the real app; Part B exercises the table and the two functions directly,
the only way currently possible.

## Part B — exercising `web_citation_record` and `record_web_citations` directly

Keep a `psql` session open in a second terminal:

```
scripts/dev.sh psql
```

### 10. Build the row shape for a cited result

```bash
podman compose exec api python3 - <<'PY'
from datetime import datetime, UTC
from askwell.websearch import WebSearchResult, web_citation_record

result = WebSearchResult(
    source="example.com",
    title="Office locations",
    url="https://example.com/offices",
    passage="The office is on the third floor.",
    retrieved_at=datetime(2026, 9, 22, 12, 0, 0, tzinfo=UTC),
)
record = web_citation_record(result, claim_ordinal=0)
print(record)
PY
```

**You should see:** `WebCitationRecord(claim_ordinal=0, domain='example.com',
title='Office locations', url='https://example.com/offices', passage='The office is on the
third floor.', retrieved_at=datetime.datetime(2026, 9, 22, 12, 0, tzinfo=datetime.timezone.utc))`
— exactly the ticket's five fields, tied to the claim that used it.

### 11. Write it alongside a message, in one transaction, and read it back

```bash
podman compose exec api python3 - <<'PY'
import asyncio, os, uuid
from datetime import datetime, UTC
from sqlalchemy import text
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from askwell.websearch import WebSearchResult, web_citation_record, record_web_citations

async def main():
    url = os.environ["ASKWELL_DATABASE_URL"].replace("postgresql://", "postgresql+psycopg://", 1)
    engine = create_async_engine(url)
    factory = async_sessionmaker(engine, expire_on_commit=False)
    result = WebSearchResult(
        source="example.com", title="Office locations",
        url="https://example.com/offices",
        passage="The office is on the third floor.",
        retrieved_at=datetime(2026, 9, 22, 12, 0, 0, tzinfo=UTC),
    )
    async with factory() as db:
        conv = (await db.execute(text(
            "INSERT INTO conversations DEFAULT VALUES RETURNING id"))).scalar_one()
        message_id = (await db.execute(text(
            "INSERT INTO messages (conversation_id, role, content) "
            "VALUES (:c, 'assistant', 'The office is on the third floor.') RETURNING id"),
            {"c": conv})).scalar_one()
        await record_web_citations(
            db, message_id=message_id,
            records=[web_citation_record(result, claim_ordinal=0)],
        )
        await db.commit()
        print("message_id:", message_id)
    await engine.dispose()

asyncio.run(main())
PY
```

**You should see:** the printed `message_id`. Note it, then in the `psql` session:

```sql
SELECT claim_ordinal, domain, title, url, passage, retrieved_at
FROM web_citations WHERE message_id = '<paste the id here>';
```

**You should see:** one row, `claim_ordinal = 0`, `domain = example.com`,
`title = Office locations`, `url = https://example.com/offices`,
`passage = The office is on the third floor.`, `retrieved_at = 2026-09-22 12:00:00+00` — read
back with `psql` alone, no network access of any kind involved in either the write or the read.

### 12. Two results from the same domain store as two separate rows

Re-run step 11 with a second `web_citation_record` call using a different passage (e.g. "The
office closes at five.") and `claim_ordinal=1`, same `url`, appended to the same `records` list
before `record_web_citations`.

**You should see:** two rows for that `message_id` in the query from step 11, `claim_ordinal` 0
and 1, both carrying the same `url` and `domain` but different `passage` values — same domain,
stored separately, exactly as the ticket's own edge case requires.

### 13. A retrieval timestamp is mandatory at the row's own shape

```
scripts/dev.sh psql -c "INSERT INTO web_citations (message_id, claim_ordinal, domain, title, url, passage) SELECT id, 0, 'example.com', 'Title', 'https://example.com', 'passage' FROM messages LIMIT 1;"
```

**You should see:** an error — `null value in column "retrieved_at" ... violates not-null
constraint`. This is the ticket's own Validation Rule enforced at the database itself: nothing
that bypasses `record_web_citations` can produce an undated row either.

### 14. A stored web citation is never updated, and the URL going stale does not touch it

The row from step 11 points at `https://example.com/offices`, a domain that will never actually
resolve to that page. Confirm nothing in this codebase re-checks it:

```
grep -rn "web_citations" api/src/askwell/ | grep -v test_
```

**You should see:** only `db/models.py` (the table definition) and `websearch.py`
(`record_web_citations`, an `INSERT` only — no `UPDATE`, no `SELECT` that feeds back into a
write). There is no code path anywhere that reads this table and writes to it again, so a URL
that stops resolving after the row is written has no way to change what is stored — the stored
title, passage and date stand exactly as read, forever.

### 15. A web citation is cascade-deleted with its message, and only with it

```sql
DELETE FROM messages WHERE id = '<paste the message_id from step 11>';
SELECT count(*) FROM web_citations WHERE message_id = '<same id>';
```

**You should see:** the `DELETE` succeeds, and the count comes back `0` — the web citation has
no independent lifetime once the turn that produced it is gone, the same lifecycle `citations`
already has with `messages`.

### 16. Confirm the corpus from Part A is untouched by any of Part B

```
scripts/dev.sh psql -c "SELECT (SELECT count(*) FROM documents) AS documents, (SELECT count(*) FROM chunks) AS chunks;"
```

**You should see:** `documents = 1`, `chunks` the same small positive number noted after step 6.
Six inserts, one failed insert, and two deletes against `messages`/`web_citations` later, nothing
in `documents` or `chunks` moved — `web_citations` has no foreign key into either table, by
design (a web result was never a chunk).

## Known gaps

- **No caller wires `escalate_web_search`'s results into `record_web_citations`.** Building an
  answer that actually cites a web result — deciding which claim ordinal a web result maps to,
  and calling `record_web_citations` alongside the `messages`/`citations` insert — is not this
  ticket's job; it stores the row shape and the write path, given a caller that already has a
  used result in hand. That caller does not exist yet, same as `M6.5-WEB-BE-185`'s escalation
  call site and `M6.5-WEB-BE-188`'s fetch path. Do not report "asking a question never produces a
  web citation" as a defect.
- **No rendering.** `M6.5-WEB-FE-190` (collapsed turn, trace, export) is separate, unbuilt work.
  Nothing in `web/` reads `web_citations` at all yet.
- **No export wiring checked here.** The ticket's own testing note ("export the conversation and
  confirm the dates travel with it") depends on the export job reading `web_citations`, which is
  not built — `M7-LOG-BE-155`'s export predates this table. Not exercised above.
- **`Citation` and `WebCitation` are deliberately unrelated tables**, not variants of one shape —
  step 3's schema comparison is what this walkthrough can check today; there is no shared query
  or shared rendering path yet to prove they never collide at read time, since nothing reads
  either for rendering.
