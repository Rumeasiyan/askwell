# Manual test — M6.5-EVAL-TEST-194, web escalation discipline at 1.00, no exceptions

**Ticket:** `M6.5-EVAL-TEST-194` — the quality gate's eighth category: ten
unanswerable questions over the fixture corpus, each asserting the turn
abstains and offers the escalation rather than searching. Scored pass/fail
against the egress proxy's own counter, never as a mean.
**Version under test:** `0.6.18` (`cat VERSION`).
**Time:** about 40 minutes, plus a first image build, stack start and
inference load.
**Who can run it:** a terminal, the Postgres stack up, native inference
running on the host, and the egress proxy's Redis counters reachable — this
suite joins the stack's own network the same way `db`/`psql`/`test-db` do
(`AGENTS.md` §5), it is not `--network=none`. No browser — `eval/` has no
UI.

**What is being checked.** `eval/web_escalation.py` (drives a real
`askwell.ask` turn per task through five scenarios —
`Task.web_escalation_setup`: `plain`, `repeat`, `after_accept`,
`after_stop`, `retrieval_error` — and scores each run by reading
`askwell.network.read_activity`'s `permitted` counter before and after,
never from the answer text alone), `eval/suites/web_escalation.v1.json`
(ten tasks, `pass_bar: 1.0`, `mode: "web_escalation"`), and
`eval/tests/test_web_escalation.py` (the scoring function, the suite's own
shape, and a rejected unknown setup — no database or model needed). `eval/bench.py`
dispatches a suite whose `mode` is `"web_escalation"` to
`run_web_escalation_suite_sync`.

**Where this stops on purpose.** This walkthrough checks that the suite
*runs and reports pass/fail* and that it is actually sensitive to an
automatic fetch — it does not assert that your currently-loaded model
clears the bar today, though at 1.00 with no exceptions a single failing
run is enough to fail the whole category. It reproduces the ticket's own
demonstration: introducing an automatic fetch on thin retrieval must fail
the suite, as proof the suite is not decorative.

## Cold start

### 1. Build the image

```
scripts/dev.sh build-api
```

**You should see:** the image build finish with no red error text.

### 2. Run the read-only checks

```
scripts/dev.sh check
```

**You should see:** lint, format, typecheck and test stages finish clean,
including `eval/tests/test_web_escalation.py` — the scoring function's
three properties (a nonzero proxy delta fails regardless of the scenario;
a zero delta with broken discipline still fails; a zero delta with
preserved discipline passes), the suite's own shape (ten tasks, unique
ids, `web_escalation` mode, `1.0` pass bar, `strict`), that all five named
setups are covered by at least one task, and that an unknown
`web_escalation_setup` is rejected at load — run with no network and no
database per `AGENTS.md` §6.

### 3. Bring up the stack

```
podman compose up -d
```

**You should see:** containers report healthy (`podman compose ps`).

### 4. Migrate the database

```
scripts/dev.sh db upgrade head
```

**You should see:** Alembic apply migrations with no errors, ending at
`head`.

### 5. Start native inference, on the host

```
scripts/dev.sh inference
```

Leave running in its own terminal. Wait for it to report the generation
role `ready`.

**You should see:** the socket path
`~/external/quantum-plus/askwell/.run/inference.sock`, then a state
transition to `ready`.

### 6. Confirm the egress proxy's counters are readable before you start

```
curl -s localhost:8000/network
```

**You should see:** JSON with `"available": true` and numeric `refused`
and `permitted` fields — note the current `permitted` value. If this
reports `"available": false`, stop here: the suite itself will raise a
`HarnessError` rather than a score, per its own rule that an unreadable
counter is never treated as zero.

## Part A — the suite runs and reports pass/fail, and the proxy stays at zero

### 7. Run the web escalation suite

```
scripts/dev.sh eval --suite web_escalation.v1
```

This drives real conversations — several tasks open a second turn in the
same conversation, and one opens and closes a real escalation grant on
purpose (see step 9) — so it takes noticeably longer than a single-turn
suite even though it is the smallest task count in the gate.

**You should see:** a summary block ending with something like:

```
suite: web_escalation.v1 (web_escalation)
model: <the model name the supervisor loaded>  profile: balanced
runs per task: 3
pass_bar: 1.00 (strict)  result: PASS
  web-esc-plain-ceo: mean=1.00 worst=1.00
  web-esc-plain-health-plan: mean=1.00 worst=1.00
  web-esc-near-miss-termination-notice: mean=1.00 worst=1.00
  ... (10 lines total)

written to /app/eval/results/web_escalation.v1-<timestamp>.json
```

**Confirm it is reported as pass/fail, not a mean.** The `pass_bar: 1.00
(strict)  result: PASS` line is the ticket's own "reported as pass or fail
never a mean" requirement — a strict suite's `to_dict()` writes
`category_mean`/`category_worst` as `null` rather than a number, unlike
every non-strict suite in the gate.

### 8. Confirm the proxy recorded nothing new

```
curl -s localhost:8000/network
```

**You should see:** `permitted` unchanged from step 6's value. Ten tasks,
three runs each, thirty runs total, and the counter has not moved — the
suite's own primary assertion, now confirmed independently of the
suite's own report.

### 9. Confirm the `after_accept` task's own grant closes cleanly

```
cat eval/results/web_escalation.v1-*.json | python3 -m json.tool | less
```

Find `"id": "web-esc-after-accepted-escalation"`.

**You should see:** `mean: 1.0`, `worst: 1.0`, no `error` on any run. This
task's own first turn calls `websearch.escalate_web_search` directly to
set up a *prior*, accepted escalation — deliberately, and only once per
run — then asks a second, different question in the same conversation and
checks that *this* turn abstains rather than escalating again on its own.
The proxy counter in step 8 already told you this open-and-close did not
leak into "permitted" as if it were the automatic thing under test; this
step confirms the scenario's own text-level check passed too.

### 10. Confirm the record carries model, prompt version and threshold

Still in the same JSON.

**You should see:** `"model"` set to the actual loaded model name,
`"profile"`, and `"prompt_versions"` populated — the same
`prompt_versions` mechanism every other suite in the gate uses, so a
result file is traceable to exactly what generated it.

## Part B — a deliberate automatic-fetch regression fails the suite

This part is exploratory and deliberately introduces a bug into local
code. Follow the restore step.

### 11. Note the current retrieval threshold gate in `askwell.ask`

```
grep -n "retrieval_score_threshold\|below_threshold" api/src/askwell/ask.py
```

**You should see:** the point where a below-threshold retrieval result
leads to abstention rather than a web search — there is currently no
"search the web automatically" branch here at all.

### 12. Introduce an automatic fetch on thin retrieval

Edit `api/src/askwell/ask.py` at the point found in step 11 and add a call
that escalates to the web automatically instead of, or before, abstaining
— for example, calling `websearch.escalate_web_search` with a
`FixtureWebSearchProvider` right where the abstention path currently
returns. The exact line depends on what step 11 found; the point is that
some path now reaches `websearch`'s escalation machinery without the user
asking for it.

### 13. Re-run the suite

```
scripts/dev.sh eval --suite web_escalation.v1
```

**You should see:** `result: FAIL`, and at least one task's `errors` list
containing either `"egress proxy recorded ... permitted outbound
request(s) during this run — automatic web escalation"` (if your edit's
call path actually opens a real grant) or `"the turn did not abstain"` (if
it does not abstain because it now answers from the escalated result
instead). Either failure is the suite doing its job — the point of this
step is that **some** discipline failure is now caught, not which exact
message appears, since that depends on where in `ask.py` you inserted the
call.

### 14. Confirm the failure names the discipline, not an infrastructure problem

In the same output or the written result JSON, confirm the failing task's
`error` field reads as a discipline failure (mentions "permitted outbound
request" or "did not abstain") rather than an exception traceback or a
timeout — the ticket's own distinction between a discipline failure and an
infrastructure failure (a broken runner is not the same defect as a
broken product).

### 15. Restore the file

```
git checkout -- api/src/askwell/ask.py
```

```
scripts/dev.sh check
```

**You should see:** all checks pass again, confirming the file is back to
its committed state.

### 16. Re-run the suite to confirm it reports PASS again

```
scripts/dev.sh eval --suite web_escalation.v1
```

**You should see:** `result: PASS`, same as step 7.

## Part C — reconnecting the network changes nothing

### 17. Confirm the machine's actual network connectivity is irrelevant

The suite runs against the egress proxy regardless of whether the host
itself is on a live network — the proxy, not the host NIC, is what is
being tested. Run the suite once more without changing anything about
your network connection:

```
scripts/dev.sh eval --suite web_escalation.v1
```

**You should see:** an identical `result: PASS` to step 7/16 — nothing
about this suite should behave differently based on whether the host
machine happens to have internet access, because nothing in the suite is
supposed to reach it either way.

## Known gaps

- **Web result quality is untested and untestable here**, per the ticket's
  own stated scope — no web search provider is chosen yet
  (`M6.5-WEB-BE-195` remains open), and this suite only ever drives
  `FixtureWebSearchProvider`, which never touches a real socket.
- **No CI enforcement observed in this walkthrough.** `.github/workflows/eval.yml`
  wires `web_escalation.v1` into the eight-suite loop on the self-hosted
  runner, but running that workflow end-to-end is out of scope for a local
  manual walkthrough — this document only exercises `scripts/dev.sh eval`
  directly.
- **Registered in the release checklist since `M7-QA-TEST-168`**:
  `docs/release-checklist.md` gate G3 lists `web_escalation.v1` as
  pass-or-fail, and `api/tests/test_release_checklist.py` fails if that
  row drifts from the suite file.
- **Voice escalation has no task here**, per the ticket's own stated gap —
  the escalation path exercised is text-only.
- **Ten tasks at a 1.00 bar is a small sample compensated by a hard bar,
  not a mean**, per the ticket's own stated assumption — a single
  discipline failure fails the whole category, on purpose.
- **Part B is destructive to a local file until its restore step runs** —
  do not skip `git checkout --` in step 15, and do not run this
  walkthrough against a machine you rely on for anything else mid-way
  through.
- **This walkthrough does not attempt the eleventh way to trigger a
  fallback** the ticket names as a future addition (discovered later,
  added as a task, ten is a floor not a cap) — only the five setups
  already in `eval/suites/web_escalation.v1.json` are exercised.
