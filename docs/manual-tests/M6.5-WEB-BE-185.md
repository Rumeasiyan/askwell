# Manual test — M6.5-WEB-BE-185, the search provider behind an interface, called only on explicit request

**Ticket:** `M6.5-WEB-BE-185` — a `WebSearchProvider` interface (question in, results with source,
title, URL, passage and retrieval time out), a `FixtureWebSearchProvider` implementation selected
by configuration, and exactly one call site (`escalate_web_search`) reachable only from an
accepted per-question escalation — proved structurally, not by convention, with a test asserting
**zero** calls to the provider when the whole answer path runs over a corpus that answers nothing.
**Version under test:** `0.6.10`
**Time:** about 40 minutes. No native inference GPU/CPU tier matters here — the fixture provider
never touches the network either way.

**What is being checked.** `api/src/askwell/websearch.py`: `WebSearchProvider` (the `Protocol`),
`WebSearchResult`, `FixtureWebSearchProvider`, `build_web_search_provider` (the one place
`Settings.web_search_provider` selects an implementation), and `escalate_web_search` (the single
call site, which records every invocation to `audit_interactions` before returning).

**This is a backend-only ticket with no product surface yet.** `M6.5-WEB-FE-186` (the offer UI)
and `M6.5-WEB-SEC-187` (egress authorisation) are not built — `web/` has no "search the web"
button or link anywhere, and nothing in the running app can accept an escalation by clicking.
Read "Known gaps" before reporting anything about a missing offer as a defect. Part A below proves
the structural guarantee (`askwell.ask` never reaches this module) through the real, running app;
Part B exercises the interface itself the only way currently possible — directly, the same way
`AGENTS.md` §5's `podman compose exec api askwell-verify` reaches into the running container for
anything that has no HTTP surface of its own yet.

`office-hours.txt`. Nothing on this screen offers a web search — there is no such control

### 7. Ask several questions the corpus plainly does not cover

Start a new conversation for each and ask, one at a time:

**You should see:** for every one, Askwell abstains — it states it has nothing in your files that

**You should see:** `0`. Six questions went through the real answer path — one answered, five
abstained — and none of them produced a call to the provider. This is the ticket's own structural
acceptance criterion (`test_the_full_answer_path_never_calls_the_provider` proves the same thing
automatically, over a fresh corpus, against a real Postgres); this step confirms it against the
actual running app rather than only the test suite.

## Part B — exercising the interface directly, since nothing in the product can reach it yet

`escalate_web_search` has exactly one caller today, and that caller does not exist as a clickable
surface. The only way to observe the interface itself is to call it the way `AGENTS.md` §5's
`podman compose exec api askwell-verify` reaches anything with no HTTP route: exec into the
already-running, already-networked `api` container. Keep a `psql` session open in a second
terminal for reading the audit rows each step writes:

```
scripts/dev.sh psql
```

### 10. No provider configured is "unavailable", not a crash

```bash
podman compose exec api python3 - <<'PY'
import asyncio, os, uuid
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from askwell.config import Settings
from askwell.websearch import escalate_web_search

async def main():
    url = os.environ["ASKWELL_DATABASE_URL"].replace("postgresql://", "postgresql+psycopg://", 1)
    engine = create_async_engine(url)
    factory = async_sessionmaker(engine, expire_on_commit=False)
    settings = Settings()
    assert settings.web_search_provider is None, "expected the unconfigured default"
    async with factory() as db:
        outcome = await escalate_web_search(
            settings, db,
            conversation_id=uuid.uuid4(), message_id=uuid.uuid4(),
            question="what time do they open?",
        )
        await db.commit()
    print(outcome)
    await engine.dispose()

asyncio.run(main())
PY
```

**You should see:** `WebSearchOutcome(status='unavailable', results=(), reason='no provider
configured')` — the deliberate distinction: this is `.env`'s real, un-edited default, and it fails
soft, not with a traceback.

### 11. A known question against the fixture returns a full result

```bash
podman compose exec api python3 - <<'PY'
import asyncio, os, uuid
from datetime import datetime, UTC
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from askwell.config import Settings
from askwell.websearch import escalate_web_search, FixtureWebSearchProvider, WebSearchResult

RESULT = WebSearchResult(
    source="example.com", title="Office locations",
    url="https://example.com/offices",
    passage="The Baker Street office opens at nine.",
    retrieved_at=datetime.now(UTC),
)

async def main():
    url = os.environ["ASKWELL_DATABASE_URL"].replace("postgresql://", "postgresql+psycopg://", 1)
    engine = create_async_engine(url)
    factory = async_sessionmaker(engine, expire_on_commit=False)
    settings = Settings().model_copy(update={"web_search_provider": "fixture"})
    provider = FixtureWebSearchProvider({"opening hours?": [RESULT]})
    async with factory() as db:
        outcome = await escalate_web_search(
            settings, db,
            conversation_id=uuid.uuid4(), message_id=uuid.uuid4(),
            question="opening hours?", provider=provider,
        )
        await db.commit()
    print(outcome)
    await engine.dispose()

asyncio.run(main())
PY
```

**You should see:** `status='ok'`, one result carrying `source='example.com'`,
`title='Office locations'`, `url='https://example.com/offices'`, the passage, and a
`retrieved_at` timestamp — the ticket's own four fields plus the retrieval time.

### 12. A question the fixture does not recognise is "nothing matched", not an error

Re-run step 11's script with the question changed to `"anything else?"` (still `provider =
FixtureWebSearchProvider({"opening hours?": [RESULT]})`, which has no entry for that string).

**You should see:** `WebSearchOutcome(status='no_results')` — a real, distinct outcome from
`unavailable`, so a caller could say "nothing matched" plainly rather than treating it as a
failure.

### 13. A result with no usable passage is dropped, not shown as an empty citation

Edit step 11's `RESULT.passage` to `"   "` (whitespace only) and re-run.

**You should see:** `status='no_results'` again — the single candidate was dropped for having
nothing usable, which reads identically to the provider genuinely finding nothing, never as a
citation with a blank quote.

### 14. A result with a URL that will not resolve is kept anyway, with its URL and date

Edit step 11's `RESULT` to `url="https://example.com/moved-or-gone-eventually"`, passage restored
to real text, and re-run.

**You should see:** `status='ok'` with the result present, `url` unchanged and `retrieved_at`
still set — the citation stays honest about what was seen and when, even for a link that may not
resolve later; only a missing passage disqualifies a result, never an unverifiable URL.

### 15. An unreachable provider is recorded as "unavailable", with its reason

```bash
podman compose exec api python3 - <<'PY'
import asyncio, os, uuid
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from askwell.config import Settings
from askwell.websearch import escalate_web_search, WebSearchUnavailable

class _Failing:
    async def search(self, question):
        raise WebSearchUnavailable("connection refused")

async def main():
    url = os.environ["ASKWELL_DATABASE_URL"].replace("postgresql://", "postgresql+psycopg://", 1)
    engine = create_async_engine(url)
    factory = async_sessionmaker(engine, expire_on_commit=False)
    settings = Settings().model_copy(update={"web_search_provider": "fixture"})
    async with factory() as db:
        outcome = await escalate_web_search(
            settings, db,
            conversation_id=uuid.uuid4(), message_id=uuid.uuid4(),
            question="q", provider=_Failing(),
        )
        await db.commit()
    print(outcome)
    await engine.dispose()

asyncio.run(main())
PY
```

**You should see:** `WebSearchOutcome(status='unavailable', results=(), reason='connection
refused')` — distinct from "nothing matched" (step 12), so the surface could tell a user "the
provider could not be reached" rather than "nothing found".

### 16. A provider that never answers is abandoned at the timeout, not left hanging

```bash
podman compose exec api python3 - <<'PY'
import asyncio, os, uuid
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from askwell.config import Settings
from askwell.websearch import escalate_web_search

class _Slow:
    async def search(self, question):
        await asyncio.sleep(3600)
        raise AssertionError("unreachable")

async def main():
    url = os.environ["ASKWELL_DATABASE_URL"].replace("postgresql://", "postgresql+psycopg://", 1)
    engine = create_async_engine(url)
    factory = async_sessionmaker(engine, expire_on_commit=False)
    settings = Settings().model_copy(update={
        "web_search_provider": "fixture", "web_search_timeout_seconds": 0.5,
    })
    async with factory() as db:
        outcome = await escalate_web_search(
            settings, db,
            conversation_id=uuid.uuid4(), message_id=uuid.uuid4(),
            question="q", provider=_Slow(),
        )
        await db.commit()
    print(outcome)
    await engine.dispose()

asyncio.run(main())
PY
```

**You should see:** the command returns in about half a second (not an hour), printing
`WebSearchOutcome(status='unavailable', results=(), reason='timed out')`.

### 17. An unknown provider name fails loudly, not silently

```bash
podman compose exec api python3 - <<'PY'
from askwell.config import Settings
from askwell.websearch import build_web_search_provider

settings = Settings().model_copy(update={"web_search_provider": "bing"})
build_web_search_provider(settings)
PY
```

**You should see:** a traceback ending in `askwell.config.ConfigurationError:
ASKWELL_WEB_SEARCH_PROVIDER='bing' is not a known web search provider. Known providers:
['fixture'].` — a typo in configuration is surfaced at the point it is read, not folded into
"unavailable" alongside a genuine outage.

### 18. Every one of steps 10–16 is on the record

In the `psql` session opened before Part B:

```sql
SELECT kind, payload->>'question', payload->>'provider', payload->>'status',
       payload->>'reason', payload->>'result_count'
FROM audit_interactions
WHERE kind = 'web_search_escalated'
ORDER BY occurred_at;
```

**You should see:** one row per escalation run above (steps 10, 11, 12, 13, 14, 15, 16 — seven
rows; step 17 raised before reaching the call site, so it wrote nothing), each `kind` =
`web_search_escalated`, and `status`/`reason`/`result_count` matching what was printed at each
step. No result content (no passage, no URL) is stored here — only that the escalation happened
and what came of it, per the ticket's own scope; the content itself belongs to `M6.5-WEB-BE-189`.

## Known gaps

- **No escalation UI or API route exists.** `M6.5-WEB-FE-186` (the offer, shown after an
  abstention) and `M6.5-WEB-SEC-187` (egress authorisation for the real provider) are unbuilt.
  There is no button, link, or endpoint in the running app that reaches `escalate_web_search` —
  Part B above calls it directly inside the `api` container, which is genuinely the only way to
  reach it today. Do not report "no offer appears after abstaining" as a defect; that is exactly
  the state this ticket leaves things in on purpose.
- **No real provider.** `FixtureWebSearchProvider` is the only implementation. The concrete
  provider (`ddgs`, per `docs/decisions.md` 2026-08-26) is `M6.5-WEB-BE-195`; nothing in this
  walkthrough reaches the actual internet, by design (C1).
- **No page-content fetching.** A result's `passage` here is whatever the provider returned
  directly; fetching and capping the linked page's own content is `M6.5-WEB-BE-188`, separate
  work.
- **Step 8's "twenty abstaining questions" from the ticket's testing notes is reduced to five
  here** for a walkthrough a person can reasonably click through by hand; the exhaustive form of
  this same proof is `test_the_full_answer_path_never_calls_the_provider`
  (`api/tests/test_websearch.py`), which is the stronger guarantee since it runs against a fresh,
  empty corpus every time rather than whatever happens to be indexed on this machine.
- **No HTTP listing of individual escalations** — reading `audit_interactions` in step 18 uses
  `psql` directly, the same way `M7-UPDATE-BE-161`'s manual test reads its own decisions table,
  because no admin console surface for this exists yet either.
