# Manual test — M6.5-WEB-SEC-187: per-question egress authorisation, opened and closed at the proxy

## Before you start

This ticket built the grant mechanism at the egress proxy, not the escalation
offer that would trigger it from the app. `M6.5-WEB-FE-186` — the button a
user clicks to accept a web search escalation — has not landed yet, so there
is no click path in the app that opens a grant. `docs/BRAIN.md`'s `0.6.11`
entry confirms this directly: "the escalation offer itself... is now the only
thing standing between this mechanism and a real user-facing escalation."

This walkthrough is in two parts:

- **Part A** is the real user path: cold start, ask a question, open
  Settings by clicking, and read the network-activity statement that this
  ticket's grants will eventually feed. Everything here is clickable today.
- **Part B** exercises the grant mechanism itself, the way the ticket's own
  Testing Notes describe it — from inside a container, against the real
  proxy and real Redis. This is what a tester has to do until
  `M6.5-WEB-FE-186` gives the mechanism a button. It is not a substitute for
  walking Part A; it is what stands in for "accept the escalation" today.

Bring up the stack first: `podman compose up -d`. Give it a minute to report
healthy — the egress proxy has to have started and registered with Redis
before either part's numbers mean anything.

---

## Part A — the user path (cold start through Settings)

1. Open Askwell in the browser at `http://127.0.0.1:8000` (or whatever
   `ASKWELL_PORT` is set to in `.env`). If this is a genuinely first run,
   complete first-run setup as prompted.
   **Expect:** the app loads to the Ask screen, with a left-hand rail
   showing Ask, Library, Clarifications, Memory and Settings.

2. Ask any question that your material can answer (or, if nothing is
   indexed yet, any question at all).
   **Expect:** an answer or an abstention appears. Either is fine here — this
   step exists only to put one ordinary turn through the system before
   looking at the counters, so a zero later is a *measured* zero rather than
   "the app was never used."

3. Click **Settings** in the left-hand rail.
   **Expect:** the Settings screen opens, with sections for Hardware
   profile, Folders you've added, Retrieval threshold, Storage, and
   **Privacy and security**.

4. Scroll to **Privacy and security** and find its **Network activity**
   subsection.
   **Expect:** a sentence of the form "**N** outbound requests permitted ·
   **M** refused, measured by the egress proxy itself. Not a setting — this
   is what actually happened." With nothing escalated yet, permitted reads
   **0**. If it instead says "Unavailable — the egress proxy's counters
   could not be read," the proxy or Redis is not up; fix that before
   continuing, since every later step depends on this figure being real.

5. Ask two or three more ordinary questions, then return to Settings.
   **Expect:** the permitted count is still **0** and does not move — nothing
   in today's app has a way to open a grant, so ordinary use cannot make
   this number change. (This is also today's honest answer to the ticket's
   own cold-start scenario "ask a second question and confirm no further
   permitted requests appear" — there is no *first* permitted request to
   compare against yet, because nothing can trigger one from the UI.)

6. Restart the stack: `podman compose down && podman compose up -d`, then
   reopen Settings → Privacy and security.
   **Expect:** permitted is **0** again (a fresh, honest measurement, not a
   persisted one — the proxy's counters live in Redis and reset with it) and
   the statement does not say "Unavailable" once the proxy has had a moment
   to re-register.

## Part B — the grant mechanism itself (container-level, until Part A has a trigger)

These steps get a shell inside the **running** `api` container, which is
already on the same internal network as `redis` and `egress-proxy` — this is
the same access the ticket's own scenario "from inside a container, attempt
a request to an unrelated host" assumes.

7. Get a shell in the running API container:
   ```
   podman compose exec api bash
   ```
   **Expect:** a shell prompt inside the container. `python3 -c "print(1)"`
   should work with no network setup needed.

8. From that shell, open a grant the way `escalate_web_search` would, and
   confirm it opened where the proxy reads it:
   ```
   python3 -c "
   import asyncio
   from askwell.config import load_settings
   from askwell import egress

   settings = load_settings()

   async def main():
       opened = await egress.open_grant(
           settings, turn_id='manual-test-1',
           destination=f'{settings.web_search_destination_host}:{settings.web_search_destination_port}',
           accepted=True, ttl_seconds=30,
       )
       print('opened:', opened)

   asyncio.run(main())
   "
   ```
   **Expect:** prints `opened: True`.

9. Confirm the grant is really sitting in Redis with a hard expiry, from the
   same shell:
   ```
   redis-cli -h redis GET askwell:egress:grant:manual-test-1
   redis-cli -h redis TTL askwell:egress:grant:manual-test-1
   ```
   **Expect:** `GET` returns `html.duckduckgo.com:443` (or whatever
   `ASKWELL_WEB_SEARCH_DESTINATION_HOST`/`_PORT` are set to). `TTL` returns a
   number just under 30, counting down on repeated calls.

10. While that grant is open, prove the proxy forwards to the granted
    destination and refuses everything else, from the same container shell:
    ```
    curl -x http://egress-proxy:3128 -sS -o /dev/null -w "granted destination: %{http_code}\n" \
      https://html.duckduckgo.com/
    curl -x http://egress-proxy:3128 -sS -o /dev/null -w "unrelated host: %{http_code}\n" \
      https://example.com/
    ```
    **Expect:** the first line reports a real HTTP status from DuckDuckGo
    (`200`/`301`/`302` — anything but a connection failure means the tunnel
    was forwarded). The second line either shows curl reporting a proxy
    `CONNECT` failure or an HTTP `403` — either way, `example.com` is never
    reached. Cross-check in Settings (Part A, step 4): refused count has
    gone up by one, and its "most recent refusals" list names
    `example.com:443`.

11. Close the grant explicitly and confirm the granted destination stops
    working immediately — the ticket's "turn ends, grant is gone" behaviour:
    ```
    python3 -c "
    import asyncio
    from askwell.config import load_settings
    from askwell import egress

    settings = load_settings()
    asyncio.run(egress.close_grant(settings, 'manual-test-1'))
    "
    redis-cli -h redis GET askwell:egress:grant:manual-test-1
    curl -x http://egress-proxy:3128 -sS -o /dev/null -w "after close: %{http_code}\n" \
      https://html.duckduckgo.com/
    ```
    **Expect:** `GET` returns `(nil)`. The `curl` line no longer reaches
    DuckDuckGo (refused, same as step 10's second line) — the same
    destination that was reachable in step 10 is refused the moment the
    grant closes, with no proxy restart involved.

12. Prove the hard expiry works even without step 11's explicit close —
    the "missed code path" edge case. Repeat step 8 with a short TTL:
    ```
    python3 -c "
    import asyncio
    from askwell.config import load_settings
    from askwell import egress

    settings = load_settings()
    asyncio.run(egress.open_grant(
        settings, turn_id='manual-test-2',
        destination=f'{settings.web_search_destination_host}:{settings.web_search_destination_port}',
        accepted=True, ttl_seconds=3,
    ))
    "
    sleep 4
    redis-cli -h redis GET askwell:egress:grant:manual-test-2
    ```
    **Expect:** `(nil)` — Redis expired the key on its own; nothing had to
    call `close_grant`.

13. Prove a grant cannot be opened without acceptance behind it — the "the
    application asks for a grant with no user acceptance" edge case:
    ```
    python3 -c "
    import asyncio
    from askwell.config import load_settings
    from askwell import egress

    settings = load_settings()

    async def main():
        opened = await egress.open_grant(
            settings, turn_id='manual-test-3',
            destination='example.com:443', accepted=False, ttl_seconds=30,
        )
        print('opened:', opened)

    asyncio.run(main())
    "
    podman compose logs api --since 1m | grep egress_grant_refused_unaccepted
    ```
    **Expect:** prints `opened: False`, and the log line for
    `egress_grant_refused_unaccepted` appears, naming `turn_id=manual-test-3`
    — this is the "anomaly worth reading" the ticket requires, not a silent
    no-op.

14. Confirm two grants in flight are independent — the "two escalations in
    quick succession" edge case. Open `manual-test-4` and `manual-test-5`
    with different destinations (repeat step 8's command twice with
    different `turn_id`/`destination` values, e.g. the search destination
    for one and `example.org:443` for the other), then close only one:
    ```
    python3 -c "
    import asyncio
    from askwell.config import load_settings
    from askwell import egress

    settings = load_settings()
    asyncio.run(egress.close_grant(settings, 'manual-test-4'))
    "
    redis-cli -h redis GET askwell:egress:grant:manual-test-4
    redis-cli -h redis GET askwell:egress:grant:manual-test-5
    ```
    **Expect:** `manual-test-4` is gone; `manual-test-5` still holds its
    destination. Closing one never touches the other.

15. Confirm the audit rows this ticket requires exist, by checking what
    `escalate_web_search` itself writes (not the manual grant calls above,
    which bypass the audit path — this checks the real call site):
    ```
    exit
    scripts/dev.sh psql -c "select event, payload->>'destination' from audit_interactions where event in ('web_search_grant_opened','web_search_grant_closed') order by created_at desc limit 10;"
    ```
    **Expect:** rows only appear here if `escalate_web_search` has actually
    been invoked — e.g. by running `pytest api/tests/test_websearch.py -k grant` (see Known gaps: this is a test invocation standing in for the
    still-missing UI trigger). Once it has, each opened/closed pair names
    the same destination and turn.

## Known gaps

- **No UI path opens a grant yet.** `M6.5-WEB-FE-186` (the escalation offer)
  has not landed, so Part A cannot observe a non-zero permitted count from
  clicking alone, and the ticket's own cold-start scenario ("accept the web
  escalation... confirm exactly one permitted request, named with its
  destination") is not walkable as a user yet. Re-run Part A once
  `M6.5-WEB-FE-186` ships — it should turn steps 4–5 into the real
  end-to-end check this ticket was written for.
- **The network-activity display does not yet name the permitted
  destination.** `web/components/settings/network-activity.tsx` shows
  refused requests with their destination but shows permitted only as a
  bare count — its own comment notes this is deliberately generic pending
  "a future permit (a live connection's own destination, online AI, a web
  search)" having somewhere to land. Whether that naming lands with
  `M6.5-WEB-FE-186` or needs its own follow-up is worth confirming when that
  ticket starts.
- **The search destination is a fixture, not the real provider.** Steps
  8–10 use `html.duckduckgo.com:443` because that is what
  `Settings.web_search_destination_host/_port` currently point at — a
  documented placeholder pending `M6.5-WEB-BE-195` (the real `ddgs`
  implementation). The grant mechanism itself does not change when that
  destination list does.
- **Step 15's audit rows require running the test suite or a real
  escalation, not just the manual grant calls in steps 8–14.** Those manual
  calls exercise `askwell.egress` directly, which has no audit path of its
  own — only `askwell.websearch.escalate_web_search` writes
  `web_search_grant_opened`/`_closed` rows. This is expected: the grant
  primitive and its one caller are different layers, and the ticket scopes
  the audit requirement to the caller.
