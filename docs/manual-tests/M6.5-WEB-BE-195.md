# Manual test — M6.5-WEB-BE-195, the real provider behind the escalation

**Ticket:** `M6.5-WEB-BE-195` — `DDGSWebSearchProvider`, the real implementation of the interface
`M6.5-WEB-BE-185` defined and `M6.5-WEB-FE-186`/`190`/`191`/`192` already render. Question in,
real results out, through `ddgs` (MIT, keyless, no account, no cost), pinned to its single
`"duckduckgo"` backend so the egress grant `M6.5-WEB-SEC-187` opens needs only one destination.
No change to the answer path, no billing, no key.

**Version under test:** `0.6.19`
**Time:** about 45 minutes, with a native inference process and real internet access.

**What is being checked.** `api/src/askwell/websearch.py`'s `DDGSWebSearchProvider` and
`build_web_search_provider`; `compose.yaml`'s forwarding of
`ASKWELL_WEB_SEARCH_PROVIDER`/`_DESTINATION_HOST`/`_DESTINATION_PORT`/`_GRANT_TTL_SECONDS` into
the `api` container (issue #545, fixed by this ticket); the egress grant opening and closing
around one real fetch; and the unavailable path when the provider cannot be reached. The
escalation surface itself (the offer, the result cards, the closing note) was already verified
against the fixture provider in `M6.5-WEB-FE-186`/`190`/`192` — this walkthrough exercises the
same surface but confirms it is now backed by something that actually reaches the web.

**This walkthrough needs real internet access on the host** — unlike every other manual test in
this repository, Part D and Part E deliberately dial out. Do not run this on a machine where
that is unexpected.

---

## Before you start

```
cd ~/external/quantum-plus/askwell
```

If you have never run Askwell before:

```
cp -n .env.example .env
```

Open `.env`, find `POSTGRES_APP_PASSWORD`, `SANDBOX_POSTGRES_PASSWORD`, `SANDBOX_OWNER_PASSWORD`
and `SANDBOX_READONLY_PASSWORD`, and put any word after each `=` if it is blank. Leave
`ASKWELL_WEB_SEARCH_PROVIDER` blank for Parts A–C below — Part D turns it on.

---

## Cold start

### 1. Build the interface

```
scripts/dev.sh web-build
```

**You should see:** a Next.js build finishing with a route list and no red error text.

### 2. Bring the stack up

```
podman compose up -d
```

**You should see:** `postgres`, `redis`, `egress-proxy`, `api`, `worker` reported as started.
Wait about thirty seconds.

### 3. Create the database tables

```
scripts/dev.sh db upgrade head
```

**You should see:** migration lines finish with no error.

### 4. Start native inference

```
scripts/dev.sh inference
```

Leave this running in its own terminal. **You should see:** the process report a loaded model
and stay running. Without this, no question can reach an abstention, and Parts B onward cannot
be exercised.

### 5. Open Askwell

Open a browser at:

```
http://127.0.0.1:8000
```

**You should see:** the **Ask your own material** first-run page.

### 6. Add a source with a narrow, checkable topic

Click **Add a source**. Add one file about a specific, narrow topic (e.g. a single-page PDF
about a return policy). Wait for it to reach `ready` — its row in the ingest progress list stops
showing a spinner.

### 7. Return to Ask

Click **Ask** in the left strip (or the Askwell wordmark).

---

## Part A — the offer reports unavailable while unconfigured

### 8. Ask a question the corpus does not cover

Type something clearly unrelated to what you added (e.g., if you added a return policy, ask
"What year was the Antikythera mechanism recovered from the sea?"). Press **Enter**.

**You should see:** the abstained state, and below it three options, with **Search the web**
visibly disabled (dimmer) and its cost reading *"not configured"*.

### 9. Confirm the setting endpoint agrees

```
curl -s http://127.0.0.1:8000/settings/web-search
```

**You should see:** `{"available": false}`.

---

## Part B — turning on the real provider

### 10. Stop the stack and set the real provider

```
podman compose down
```

Open `.env`, set:

```
ASKWELL_WEB_SEARCH_PROVIDER=ddgs
```

Leave `ASKWELL_WEB_SEARCH_DESTINATION_HOST`, `_PORT`, and `ASKWELL_WEB_SEARCH_TIMEOUT_SECONDS`
at whatever `.env.example` shipped — they are already the real endpoint, not placeholders.

```
podman compose up -d
```

Wait about thirty seconds.

### 11. Confirm the setting endpoint now agrees

```
curl -s http://127.0.0.1:8000/settings/web-search
```

**You should see:** `{"available": true}` — this is what closes issue #545: before this
ticket's `compose.yaml` change, setting `ASKWELL_WEB_SEARCH_PROVIDER` in `.env` alone had no
effect on the running container and this would still read `false`.

### 12. Reopen Askwell and re-add the source if needed

```
http://127.0.0.1:8000
```

A fresh `podman compose down`/`up` does not drop the database — the source from step 6 should
still show as `ready` under **Sources**; only re-add it if it does not.

## Part C — cold-start walkthrough: a real escalation with real results

### 13. Ask an uncovered question that has a genuine, checkable answer on the public web

Go to **Ask**, type a question your corpus cannot answer but that has a well-known, verifiable
answer (e.g. "What is the boiling point of water at sea level in Celsius?"). Press **Enter**.

**You should see:** the abstained state, with the three escalation options below it, **Search
the web** now enabled with its default cost caption.

### 14. Click **Search the web**

**You should see:** the cost caption changes to *"sending your question now"*, then — within a
few seconds — to *"sent — this question only"*, and a new region appears below the abstention
showing at least one result card.

### 15. Read one result card closely

**You should see:** each card shows a real, resolvable domain (e.g. `en.wikipedia.org` or
similar — not `example.com` or any fixture-looking placeholder), a real page title, a URL you
could open, a short passage of text, and a retrieval date/time reading **today's actual date**
(2026-09-22, or the date you are running this on).

### 16. Confirm a generated answer accompanies the results

**You should see:** below or alongside the result cards, generated answer text is present that
draws on those results, with citations pointing at the web result cards rather than the
provenance margin — the same "not your material" treatment `docs/web-search.md` §3/§4 describes.

### 17. Confirm the escalation is on the audit record

```
scripts/dev.sh psql -c "SELECT event_type, payload ->> 'status', payload ->> 'result_count' FROM audit_interactions WHERE event_type = 'web_search_escalated' ORDER BY id DESC LIMIT 1;"
```

**You should see:** one row, `event_type` = `web_search_escalated`, status `ok`, and a
`result_count` greater than `0`, matching what rendered.

### 18. Confirm the grant opened and closed around the fetch alone

```
scripts/dev.sh psql -c "SELECT event_type, payload ->> 'destination' FROM audit_interactions WHERE event_type IN ('web_search_grant_opened','web_search_grant_closed') ORDER BY id DESC LIMIT 2;"
```

**You should see:** two rows — `web_search_grant_closed` then `web_search_grant_opened` (newest
first), both naming the same `destination` — `html.duckduckgo.com:443` unless you changed it in
step 10.

## Part D — the next question starts local again

### 19. Ask a brand-new question, without clicking Search the web

Go back to **Ask** (a fresh turn, not the one from step 13). Ask any question — covered or
uncovered, does not matter.

**You should see:** no automatic web fetch — no result region appears unless you click
**Search the web** again on *this* turn's own abstention. The prior turn's acceptance does not
carry forward (C10 — escalation is per-question, never sticky).

### 20. Confirm the destination is refused outside an open grant

With no escalation currently in flight, try reaching the search destination directly through the
egress proxy from inside the `api` container:

```
scripts/dev.sh shell
curl -s -o /dev/null -w "%{http_code}\n" -x http://egress-proxy:3128 https://html.duckduckgo.com/html/
exit
```

**You should see:** `403` — the proxy refuses the destination when no turn has an open grant for
it, confirming the destination stays closed between escalations rather than merely being unused
by the UI.

---

## Part E — the cable unplugged: provider unreachable, abstention still stands

### 21. Stop the egress proxy to simulate no network path out

```
podman compose stop egress-proxy
```

### 22. Ask another uncovered question and accept the escalation

Ask a new uncovered question, then click **Search the web**.

**You should see:** the cost caption moves through *"sending your question now"* and lands on a
"could not be sent" / unavailable message (`docs/ux/web-search.md` §4). **You should not see:**
any result cards, any generated web answer text, or any fallback to the model's own general
knowledge — the original abstention text above the offer is unchanged and still stands as the
answer.

### 23. Confirm the audit record shows unavailable, not a crash

```
scripts/dev.sh psql -c "SELECT event_type, payload ->> 'status', payload ->> 'reason' FROM audit_interactions WHERE event_type = 'web_search_escalated' ORDER BY id DESC LIMIT 1;"
```

**You should see:** one row, status `unavailable`, with a `reason` naming a connection or
resolution failure — the escalation is on the record even though it failed.

### 24. Restart the egress proxy

```
podman compose start egress-proxy
```

Wait a few seconds, then confirm `curl -s http://127.0.0.1:8000/settings/web-search` still
reports `{"available": true}` (the provider configuration did not change — only the network path
did).

---

## Part F — turn the provider back off

### 25. Return the stack to the unconfigured default

```
podman compose down
```

Edit `.env` so `ASKWELL_WEB_SEARCH_PROVIDER=` is blank again.

```
podman compose up -d
```

**You should see:** `curl -s http://127.0.0.1:8000/settings/web-search` reports
`{"available": false}` once more, so the rest of this walkthrough (and any other ticket's)
returns to the shipped default of no outbound web search.

## Known gaps

- **Passages are `ddgs`'s own search snippets, not the fetched page.** Fetching the full page
  behind each result was scoped out of this ticket (`docs/decisions.md`, 2026-09-22; issue
  #551) — a short passage rather than a full article is expected, not a defect.
- **`ddgs` is pinned to the single `"duckduckgo"` backend, not `"auto"`.** Results will only ever
  come from that one backend. If it changes its markup upstream and starts returning nothing or
  erroring, that surfaces here as `unavailable` or `no_results` — a real, acknowledged risk
  (`docs/web-search.md` §6), not something this walkthrough can guard against in advance.
- **No component test infra exists in this repo** for the browser-rendered result cards
  (`web/package.json`'s `test` script runs `node --test` over `lib/*.test.ts` only) — this
  walkthrough and `M6.5-WEB-FE-190`/`192`'s own manual tests are the only places those states are
  exercised in a real browser.
- **Forcing "the library broken by an upstream markup change" cannot be simulated here** short of
  actually breaking `ddgs` or waiting for it to happen upstream. Part E substitutes "provider
  unreachable" (proxy stopped) for that case, which exercises the same `WebSearchUnavailable`
  path (`except DDGSException` in `DDGSWebSearchProvider.search`) but not the specific trigger.
- **Rate limiting from the `duckduckgo` backend is possible on repeated runs of this
  walkthrough in a short window.** If Part C's search returns `unavailable` with a rate-limit
  reason instead of results, wait a few minutes and retry step 14 rather than treating it as a
  regression.
