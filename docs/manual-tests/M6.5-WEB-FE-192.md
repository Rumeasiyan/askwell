# Manual test — M6.5-WEB-FE-192, the remaining states: searching, nothing found, unavailable, and the escalation closing

**Ticket:** `M6.5-WEB-FE-192` — the escalation offer's four remaining states
(`docs/ux/web-search.md` §4, `docs/states-and-edge-cases.md` §1/§7.1, C10): named progress that
says the question has left the machine while searching, a plain "nothing found" statement that
never retries or widens, a plain "can't reach the web" statement that leaves the abstention
standing as the answer, a closing note after any search that actually ran, and the collapsed-turn
web marker.

**Version under test:** `0.6.17`
**Time:** about 50 minutes — longer than most tickets in this milestone because the escalation
is not reachable through the shipped `compose.yaml` at all (issue #545, discovered while this
ticket's own author tried to verify it) and this walkthrough must apply and later revert a local
patch to get there.

**What is being checked.** `web/components/ask/ask-screen.tsx`'s `EscalationOffer` (`phase`,
`outcome`, the `Stop` control, `CollapsedTurn`'s `WebMarker`) and `web/lib/web-search.ts`'s
`webSearchDisplayStatus`, `webSearchStatusMessage`, `webSearchShowsClosedNote`,
`webSearchOptionCost`, and the four fixed-copy constants.

---

## Before you start

```
cd ~/external/quantum-plus/askwell
```

If you have never run Askwell before:

```
cp -n .env.example .env
```

Open `.env`, find `POSTGRES_APP_PASSWORD`, `SANDBOX_POSTGRES_PASSWORD`, `SANDBOX_OWNER_PASSWORD`
and `SANDBOX_READONLY_PASSWORD`, and put any word after each `=` if it is blank.

**Read this before Part 2.** Issue #545: `compose.yaml`'s `api` service never forwards
`ASKWELL_WEB_SEARCH_PROVIDER`/`_DESTINATION_HOST`/`_DESTINATION_PORT`/`_GRANT_TTL_SECONDS` into
the container's `environment:` block, so setting them in `.env` alone has no effect on the real
running stack — `GET /settings/web-search` reports `available: false` and every "Search the web"
button stays disabled, regardless of `.env`. Part 2, step 1 below applies the same local patch
the ticket's own author used to verify it (and reverted before committing) — you will revert it
the same way at the end of this walkthrough. This is a pre-existing gap in `compose.yaml`, not
something this ticket introduced or something you are expected to fix here.

You will also need a short text document whose content you control:

```
mkdir -p /tmp/askwell-fe192
cat > /tmp/askwell-fe192/return-policy.txt <<'EOF'
Return Policy

Items may be returned within thirty (30) days of purchase with a receipt,
for a full refund to the original payment method.
EOF
```

## Part 2 — cold start, walk all four states

### 1. Apply the local patch that makes the escalation reachable at all

Open `compose.yaml`, find the `api:` service's `environment:` block, and the
`ASKWELL_ROOTS_MOUNT: ${ASKWELL_ROOTS_MOUNT:-}` line inside it. Add four lines directly after it,
matching the existing `${VAR:-default}` pattern used by every other setting in that block:

```yaml
      ASKWELL_WEB_SEARCH_PROVIDER: ${ASKWELL_WEB_SEARCH_PROVIDER:-}
      ASKWELL_WEB_SEARCH_DESTINATION_HOST: ${ASKWELL_WEB_SEARCH_DESTINATION_HOST:-html.duckduckgo.com}
      ASKWELL_WEB_SEARCH_DESTINATION_PORT: ${ASKWELL_WEB_SEARCH_DESTINATION_PORT:-443}
      ASKWELL_WEB_SEARCH_GRANT_TTL_SECONDS: ${ASKWELL_WEB_SEARCH_GRANT_TTL_SECONDS:-30.0}
```

You will revert this with `git checkout -- compose.yaml` in the last step — do not commit it.

### 2. Turn the fixture provider on

Open `.env`, set:

```
ASKWELL_WEB_SEARCH_PROVIDER=fixture
```

### 3. Bring the stack up

```
podman compose up -d
```

**You should see:** `postgres`, `redis`, `egress-proxy`, `api`, `worker` reported as started.
Wait about thirty seconds.

### 4. Create the database tables (skip if already migrated)

```
scripts/dev.sh db upgrade head
```

### 5. Confirm the patch actually reached the container

```
curl -s localhost:8000/settings/web-search
```

**You should see:** `{"available":true}`. If you see `false`, the patch from step 1 did not
reach the running container — rebuild (`scripts/dev.sh build-api`) and recreate
(`podman compose up -d --force-recreate api`) before continuing.

### 6. Start native inference

```
scripts/dev.sh inference
```

Leave this running in its own terminal. **You should see:** the process report a loaded model
and stay running.

### 7. Open Askwell

```
http://127.0.0.1:8000
```

**You should see:** the **Ask your own material** first-run page (or the ordinary Ask screen if
sources already exist from an earlier session).

### 8. Add the return-policy document

Click **Add a source**, add `/tmp/askwell-fe192/return-policy.txt`, and wait for it to reach
`ready` (the ingest progress row stops showing a spinner). Return to **Ask**.

## Searching, and nothing found

### 9. Ask a question the document does not cover

Type, then press **Enter**:

```
What is our policy on returning a gift that was never opened?
```

Wait — this document does cover gifts within the same 30-day window, so if it answers normally
instead of abstaining, ask something further off-topic instead, e.g. "What is our warranty
period on electronics?"

**You should see:** the abstained state — a block of `--ink`/`--muted` text, and below it three
escalation options: **Search the web**, **Ask a larger model**, **Add a source instead**.

### 10. Click "Search the web"

**You should see, immediately:**

- The button's own cost caption changes to *"sending — your question has left this machine"*.
- Below the three options, a line reading exactly **"Searching the web — your question has left
  this machine."**, next to a **Stop** button.

This is the named-progress state (`web-search.md` §4's "Searching" row) — it states in words,
not just a spinner, that the question has actually left the machine.

### 11. Wait for it to settle

**You should see**, within a couple of seconds:

- The progress line and **Stop** button disappear.
- A new line reading exactly **"Nothing found on the web either."**
- Immediately below that, a second line reading exactly **"The search closed with this
  question — your next one starts local again."**
- The button's own cost caption now reads *"sent — nothing usable came back"*.

**You should not see:** any new search fire on its own, any retry, any "trying again" message,
or the abstention text above change in any way — the original abstention lines are exactly as
they were before you clicked.

### 12. Confirm this reads differently from "nothing to say" being conflated with a failure

Re-read the abstention text above the offer. **You should see** it is unchanged — the escalation
answered "nothing on the web either", it did not touch the honest local answer already given.

### 13. Escalate a second time on the same turn

Click **Search the web** again (it is still enabled).

**You should see:** the exact sequence from steps 10–11 repeats — sending, then nothing found,
then the closed note again — a second, independently authorised search, not blocked and not
silently reusing the first result.

---

## Stopping mid-search

### 14. Ask a new uncovered question

Ask something else the document does not cover, e.g. "What is the CEO's name?" Confirm it
abstains and the offer appears again.

### 15. Click "Search the web", then immediately click "Stop"

**You should see:** the progress line and Stop button appear, then — the instant you click
Stop — both disappear, the button's cost caption reverts to its default (*"sends your question
out · this question only"*), and **no** "nothing found", "can't reach the web", or closed note
appears anywhere. The offer looks exactly as if it had never been clicked.

### 16. Click "Search the web" once more on this same turn

**You should see:** it runs normally to "nothing found" and the closed note, same as before —
stopping did not leave the offer stuck or the grant it opened lingering in a broken state.

## Search unavailable

### 17. Ask a third new uncovered question

Ask something else uncovered, e.g. "What is our policy on shipping internationally?" Confirm it
abstains and the offer appears, enabled.

### 18. Stop the API before clicking

```
podman compose stop api
```

Leave the browser tab open — the abstained turn and its offer are already rendered client-side
and do not need the API to stay visible.

### 19. Click "Search the web"

**You should see:**

- Briefly, the sending state from step 10 (the fetch is attempted).
- Then a line reading exactly **"I can't reach the web right now."** — `docs/web-search.md` §6's
  copy, verbatim.
- Immediately below it, the same closing note: **"The search closed with this question — your
  next one starts local again."**
- The button's cost caption reads *"could not reach the web"*.

**You should see, still:** the abstention text above the offer, completely unchanged — the
honest local answer is still standing as the answer, exactly as `web-search.md` §4's "Search
unavailable" row requires. The message never says whose fault it was (no mention of the API,
the provider, or a timeout) — matching `design-system.md` §6's ban on vague blame language.

### 20. Bring the API back

```
podman compose start api
```

Wait about ten seconds, then confirm the app is responsive again (the Ask composer accepts
input without an error).

### 21. Confirm no offline warning appears on an ordinary question

Ask a question the document *does* cover, e.g. "How many days do I have to return an item?"

**You should see:** a normal, fully-grounded streamed answer citing `return-policy.txt` ("30
days"), with **no** mention of being offline, unreachable, or unavailable anywhere on this turn
— `states-and-edge-cases.md` §1's rule that the ordinary local case never renders an offline
warning, confirmed by its absence here right after step 19 showed the warning exists at all.

## The collapsed-turn web marker

### 22. Collapse the "nothing found" turn from step 9–11

Scroll up to that turn and click its row to collapse it.

**You should see:** the row shrinks to the question, a one-line summary, and the source-count
badge (showing **"No sources"**, since it abstained) — and **no** dashed web marker beside it.

### 23. Collapse the "unavailable" turn from step 17–19

Same as step 22.

**You should see:** the same — no web marker.

Steps 22–23 are the correct behaviour, not a gap: `CollapsedTurn`'s `WebMarker` renders only
when `turn.webCitations.length > 0`, and neither "nothing found" nor "unavailable" ever
populates a citation — there was nothing to cite. Read "Known gaps" below for why the *positive*
case (a turn that actually got a web-sourced answer, then collapses keeping the marker) could
not be walked in this session.

## Known gaps

- **The escalation is unreachable through the shipped `compose.yaml` without the local patch
  applied in step 1** (issue #545, still open at the time this document was written). Every
  other manual-test document in this milestone that exercises a live escalation inherits this
  same blocker; do not report it again as a new defect against this ticket specifically — fix it
  once, by landing #545, rather than patching around it in every walkthrough forever.
- **The "answered from the web" outcome, and therefore the positive collapsed-turn web-marker
  case (§ steps 22–23 above), cannot be produced through the running app at all right now.** The
  only `WebSearchProvider` implementation that exists is `FixtureWebSearchProvider`
  (`api/src/askwell/websearch.py`), which is always built with an empty result mapping — nothing
  in `compose.yaml`, `.env`, or any endpoint lets a manual tester seed it with a recorded result.
  The real provider (`ddgs`, `M6.5-WEB-BE-195`) is not built yet. Until one of those lands, every
  live escalation resolves to "nothing found," never "answered" — this walkthrough proves the
  marker's *absence* is correct for that outcome but cannot prove its *presence* for a won one.
  The marker's rendering logic itself (`webCitations.length > 0` → dashed `--inferred` ring) is
  covered only by reading the code, not by a browser check, in this session.
- **The mixed-answer region, its claim-level attribution, and hover/keyboard pairing are
  `M6.5-WEB-FE-190`/`-191`**, already shipped and already walked in their own manual-test
  documents — not re-verified here.
- **Voice escalation is unspecified and deferred** (`docs/web-search.md` §8).
- **The trace's flagging of fetched instruction-like content is `M6.5-WEB-OBS-193`**, not this
  ticket.
- **No component test infra exists in this repo** — `web/package.json`'s `test` script runs
  `node --test` over `lib/*.test.ts` only, so this walkthrough is the only place `EscalationOffer`,
  its `Stop` control, and `CollapsedTurn`'s `WebMarker` are exercised in an actual browser.
