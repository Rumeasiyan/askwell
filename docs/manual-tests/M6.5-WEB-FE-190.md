# Manual test — M6.5-WEB-FE-190, the web results region, separate from the provenance margin

**Ticket:** `M6.5-WEB-FE-190` — a component that renders a used web result: a dashed
`--inferred`-bordered region headed *"From the web — not your files"*, showing domain, page
title, the passage used and a retrieval date, with the full URL reachable. Never inside the
provenance margin, at any width. Shares no implementation with the source card.

**Version under test:** `0.6.14`
**Time:** about 20 minutes.

**What is being checked.** `web/components/ask/web-result.tsx` (`WebResultsRegion`,
`WebResultCard`) and `web/lib/web-citations.ts` (`WebResult`, `truncate`, `truncatedTitle`,
`truncatedUrl`, `retrievedDateLabel`).

**This is an isolated-capability ticket, same shape as `M6.5-WEB-BE-185`/`-188`/`-189`.**
`WebResultsRegion` has exactly zero callers anywhere in `web/components/ask/ask-screen.tsx` or
anywhere else in `web/` today — confirmed by `grep -rn "WebResultsRegion" web/components web/app`,
which returns only the component's own file and its comment referring to itself. No live turn
carries a `WebResult`: the escalation offer (`M6.5-WEB-FE-186`) and the wiring that would let an
answer actually cite a web result (`M6.5-WEB-FE-191`/`-192`) are separate, unbuilt tickets. So
there is no click-path in the running app that reaches this component — the same reason
`M6.5-WEB-BE-189`'s manual test could not produce a web citation through the API either. Part A
below confirms the real app has nothing to show. Part B renders the component directly against
fixture data, the only way currently possible, using a temporary page deleted at the end. Read
"Known gaps" before reporting the absence of a live web result as a defect of this ticket.

## Part 3 — render the component directly, the only way currently possible

Create `web/app/scratch-web-result-190/page.tsx` with this content:

```tsx
import { WebResultsRegion } from "@/components/ask/web-result";
import type { WebResult } from "@/lib/web-citations";

const FIXTURES: WebResult[] = [

    domain: "weather.gov",
    title: "Coastal wind advisory, issued this morning",
    url: "https://www.weather.gov/advisories/coastal-wind",
    passage: "Winds up to 95 km/h are expected along the coast Thursday evening.",
    retrievedAt: "2026-09-20T14:30:00Z",
  },
  {
    domain: "example.com",
    title:
      "A Very Long Page Title That Keeps Describing Every Nuance Of The Article So Thoroughly That It Runs Well Past Any Reasonable Length For A Heading",
    url: "https://example.com/articles/2026/09/a-very-long-slug-that-keeps-going-and-going-and-going-past-any-reasonable-length-for-a-url-path-segment-in-a-browser-address-bar",
    passage: "Short.",
    retrievedAt: "2026-01-05T09:00:00Z",
  },
];

export default function ScratchWebResult190() {
  return (
    <div className="flex flex-col gap-4 p-4" style={{ maxWidth: "420px" }}>
```

This does not touch `ask-screen.tsx`, `provenance-margin.tsx`, or any product route — it mounts

### 7. Read one result in full

On the first result (weather.gov), **you should see**, top to bottom: the domain `weather.gov`
in small caps/mono; the title `Coastal wind advisory, issued this morning`, in full, not
truncated; the passage in quotation marks, in serif, at its own natural size (this is the
one-sentence-passage edge case for the second result, and the first result's own longer passage,
both un-padded to match any fixed card height); then `Retrieved 20/09/2026` (or your locale's
date format) and the URL, each in `--muted`, not `--inferred` and not `--provenance` — the
heading above is the only ochre text.

### 8. Confirm the long title and long URL truncate visibly, never silently

On the second result (example.com), **you should see:** the title cut short with a trailing `…`
well before its full text — count that it stops at 90 characters or fewer of the original, per
`TITLE_TRUNCATE_AT` in `web/lib/web-citations.ts`. The URL beneath the passage is also cut with a
trailing `…`, but **starts** with `https://example.com/` intact — the truncation removes only
the end of the path, never the scheme or domain. Hover (or long-press) each: the browser's own
title-attribute tooltip shows the full, untruncated title and URL — nothing here is ever
shortened into something that reads as a different page.

### 9. Click through, and confirm the window itself does not navigate

Click the domain, the title, or the URL on either result. **You should see:** the link open in a
**new browser tab**, and the Askwell tab stays exactly where it was, still showing the scratch
page — `target="_blank" rel="noopener noreferrer"` on every link, never an in-window navigation.

### 10. Resize below the breakpoint and confirm the region never merges into the margin

With the window wide, note that the real provenance margin `<aside>` is a separate column on the
right. Narrow the browser window (or the Askwell desktop window, once M7 ships it) past roughly
`1024px` — the app's own `@5xl` container-query breakpoint (`docs/ux/design-system.md` §4,
`web/components/shell/shell.tsx`). **You should see:** the rail and the provenance margin's own
column disappear from the layout as expected (the margin reflows inline beneath answers
elsewhere in the app, per `M1-CITE-FE-044` — there is no answer on this scratch page for it to
reflow under), while the web-results region in the main column is completely unaffected by the
width change — it was never inside that `<aside>` to begin with, at any width.

### 11. Switch to the dark theme and confirm the distinction still reads

Click the theme buttons in the header (**system** / **light** / **dark**) — click **dark**.
**You should see:** the page repaint with dark backgrounds, the dashed border and heading

recorded in step there; both the light and dark figures should match what you see). Switch back

### 12. Confirm no `--provenance` colour appears anywhere on the region

With either theme active, inspect the region (browser dev tools, "Inspect element," on the
border and the heading) or simply compare colours by eye against a real source card in the
provenance margin from Part 2. **You should see:** the web region's border and heading are the
ochre `--inferred` colour throughout; the margin's source cards use the teal/green
`--provenance` colour for their left bar. The two must never match — `--provenance` means
"traceable to a source you own," which a web page is not.

## Known gaps

- **Not reachable from the running app through any real user action.** There is no "search the
  web" offer (`M6.5-WEB-FE-186`), no live turn that carries a `WebResult`, and no wiring from a
  streamed answer into this component (`M6.5-WEB-FE-191`/`-192`). Part 3's scratch page is the
  only way to see this component rendered today, in the same sense that `M6.5-WEB-BE-189`'s
  manual test could only reach `record_web_citations` directly. Do not report "I asked a question
  and never saw a web result" as a defect of this ticket.
- **The mixed-answer case is out of scope.** A single answer citing both the user's documents and
  the web, with each claim pointing at its own kind of source, is `M6.5-WEB-FE-191`. Nothing above
  exercises that composition.
- **The searching, unavailable and closed states are out of scope.** Those are
  `M6.5-WEB-FE-192`. This ticket only covers the "Answered from the web" state's rendering.
  Loading states, provider failures and the "escalation closed" copy are unbuilt.
  `web-search.md` §4's other listed rows (Offered, Searching, Nothing found, Search unavailable,
  Instruction-like content fetched, Escalation closed) have no corresponding UI yet.
  Nothing above tests them.
- **No preview of the linked page**, and nothing archived — a page that goes offline after the
  answer is a dead link next to an honest, unchanging retrieval date. This is by design
  (`web-search.md` §3), not a gap in this ticket specifically, but it means step 9's click-through
  cannot be tested against a page guaranteed to still exist; `weather.gov` and `example.com` were
  chosen as stable domains, not because either is expected to still show this exact content.
