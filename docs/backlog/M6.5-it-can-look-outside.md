# M6.5 — It can look outside

**Goal:** When the user's own files do not cover a question, Askwell says so — and then offers to look further. The user escalates; Askwell never does.

**Phase:** 6.5 (`../build-plan.md`) · **Depends on:** M7 · **Tickets:** 11 (one blocked) · **Estimated:** 29–40 hours of unblocked work

**Exit condition:** A question the corpus cannot answer abstains first, offers the escalation below the abstention, and — only on request — returns web results in their own marked region with URLs and retrieval dates. Egress opens for that one question and closes with the turn, verified at the proxy rather than asserted in code. The web escalation discipline suite scores 1.00.

> **Sequenced after M7, before M8.** It needs the settings surface and the audit path to already exist, and it comes before credits because it is free and they are not (`../build-plan.md`). The milestone numbering is deliberately fractional so the existing milestones keep their identifiers.

---

## The one rule

**Askwell abstains first, then offers. It never searches because retrieval was thin.**

That sentence is constraint **C10** and it is the whole design (`../web-search.md`, `../ux/web-search.md`). Everything in this milestone follows from it, and **every ticket here states in its acceptance criteria how the escalation-not-fallback rule is preserved** — that is what the `constraint:web-escalation` label is for.

The danger was never the network call. It is what an automatic one does to abstention. Askwell's most-tested behaviour is saying *"your files do not cover this"*, and that is useful because it is **informative** — it tells the user something true about what they have. If the web is reached whenever retrieval comes back thin, that sentence stops happening, so it stops meaning anything, and the user loses the signal that told them their corpus had a gap. The abstention rate, which `../success-metrics.md` §2 treats as the key operational number, would fall to zero for entirely the wrong reason.

So the feature is delivered by *not* doing the obvious thing with it.

## Included epics

| Epic | Code | Covers |
| ---- | ---- | ------ |
| Web search | `WEB` | The provider interface, the offer, egress authorisation, caps, the results region, mixed answers, states, the marker |
| Evaluation | `EVAL` | The web escalation discipline suite at 1.00 |

## What is never built here

Stated up front because each of these is a reasonable-sounding change that would destroy the constraint.

| Never | Why |
| ----- | --- |
| A retry that reaches the web when retrieval scores low | It is the fallback C10 forbids, wearing a different name |
| A conversation-level or settings-level toggle | Sticky egress is how a per-unit permission becomes a default (C1 as amended) |
| Web results in the provenance margin | The margin is for material the user owns and can open (C10) |
| Chunking, embedding or persisting web content into `chunks` | It is not the user's corpus, and a hostile page must not influence a future answer it was not part of |
| Using the web to answer a question about the user's own documents | If the answer is meant to be about their contract, the web cannot supply it |

### M6.5-WEB-BE-185 — The search provider behind an interface, called only on explicit request

**Type:** Story

**User Story**
- **Actor:** the maintainer who will have to change search providers at some point, and would rather not touch the answer path to do it.
- **User Need:** one seam between Askwell and whoever is doing the searching.
- **Business Value:** the provider question is open and will stay open for a while (`../web-search.md` §6). A design that can wait for the answer is worth more than a design that has to be right about it now.
- *As someone whose local AI should not be welded to one search company, I want the provider to be a replaceable part, so that a provider going away is an afternoon rather than a rewrite.*

**Context / Background**
**Detailed Description:** The search provider sits **behind an interface, like the TTS engine**, so it can be swapped without touching the answer path (`../architecture.md` §5.2). The interface takes a question and returns results with a source domain, a page title, a URL, the passage used, and the time of retrieval.

The interface has exactly **one caller and one entry condition**: an explicit, user-initiated escalation for one question. There is no code path from retrieval scoring low to this interface, and the absence of that path is the point of the ticket rather than an incidental property of it.

The concrete provider and the billing model are open and blocked (M6.5-WEB-BLOCKED-195). This ticket builds the interface and a local fixture implementation that returns recorded results, which is enough for everything else in the milestone — including, importantly, the eval suite, which asserts that no fetch happens at all.

**Scope**
- The provider interface: question in, results out, with source, title, URL, passage and retrieval time.
- A fixture implementation returning recorded results, for development and for the eval suite.
- A single call site, invoked only from an accepted escalation.
- Configuration selecting the implementation, with no provider name in application code.
- Timeout and error surfaces that distinguish "the provider said nothing matched" from "the provider could not be reached".

**Out of Scope**
- Choosing the provider or the billing model (M6.5-WEB-BLOCKED-195).
- Fetching and capping page content (M6.5-WEB-BE-188).
- Egress authorisation (M6.5-WEB-SEC-187) — the interface cannot reach anything without it.
- Any rendering.

**Acceptance Criteria**
- **Acceptance Criteria:** The interface is defined once and implemented by the fixture. The implementation is selected by configuration and no provider name appears in application code. Calling it returns results carrying source, title, URL, passage and retrieval time. **The escalation-not-fallback rule is preserved structurally:** the interface has exactly one call site, reachable only from an accepted per-question escalation, and a test asserts that running the entire answer path over a corpus that answers nothing produces **zero calls** to it. A code path that could call it from retrieval scoring, from a retry, or from an error handler is a defect, not an optimisation.
- **Edge Cases:** The provider returns nothing — a real, distinct result meaning "nothing matched", not an error, so the surface can say so plainly and not fall back further. The provider is unreachable — distinct again, so the abstention can still stand as the answer. The provider returns a result with no usable passage — dropped rather than rendered as an empty citation. A result whose URL will not resolve — kept with its URL and its date, because the citation must remain honest even when the page has gone. The provider takes longer than the timeout — abandoned, and the turn says so.
- **Permissions / Roles:** Single user — no roles. Not applicable.
- **UI States:** None directly; consumed by M6.5-WEB-FE-190 and M6.5-WEB-FE-192. Behaviour in `../web-search.md` §2 and §6.
- **Validation Rules:** The interface may never be invoked without a live per-question authorisation. No provider name, endpoint or key may be hardcoded (C8).
- **Audit / Logging Requirements:** Every invocation is recorded with the question, the provider implementation in use, and the outcome — recorded in the interaction path established in M1-ASK-OBS-041 (C6).
- **Analytics Events:** Local counter of escalations — nothing transmitted (C1).

**Real-World Example Scenarios**
- The chosen provider changes its terms a year in; the implementation is replaced and no part of the answer path is touched.
- A well-meaning change adds a retry on thin retrieval; the zero-calls test fails and the change is rejected before it lands.

**Dependencies & Assumptions**
- **Dependencies:** M2-ABSTAIN-BE-054, M1-ASK-BE-037, M0-MODEL-BE-019.
- **API / Data Touchpoints:** The answer path; configuration; the interaction record.
- **Assumptions:** The fixture is representative enough to build and test the whole milestone against. Since the eval suite's job is to assert that **no** search happens, most of this milestone is testable with no provider at all — which is why the blocked decision does not block the work.

**Testing Notes / Scenarios**
- **Cold-start manual walkthrough:** Cold start with a small corpus and the fixture provider configured. Ask a question the corpus covers and confirm a normal cited answer. Ask twenty questions the corpus plainly does not cover, decline every offer, and then read the invocation log: it must be empty. Accept one offer and confirm exactly one invocation appears, with the question and the outcome.
- **Other scenarios:** Configure the fixture to return nothing, and confirm that reads differently from configuring it to fail. Configure it to time out and confirm the turn abandons rather than hanging. Remove the configuration entirely and confirm the escalation is offered as unavailable rather than crashing.
- **Known gaps:** No real provider — the concrete choice and the billing model are blocked (M6.5-WEB-BLOCKED-195). Nothing is fetched from a page yet; that is M6.5-WEB-BE-188. Nothing is rendered.

**Effort & Granularity Check**
- **Estimate:** 3–4 hours · **Priority:** Critical
- **Labels / Component:** `phase:6`, backend, `constraint:web-escalation`, `constraint:local-first`
- **Granularity:** One interface, one fixture and one negative test. Small because the provider decision is deliberately outside it.

### M6.5-WEB-FE-186 — The escalation offer on the abstention surface

**Type:** Story

**Human review:** copy — this ticket renders wording a user reads, specified in `docs/ux/`. The runner stops and quotes it before the pull request is merged.

**User Story**
- **Actor:** someone who has just been told, honestly, that their files do not cover the question they asked.
- **User Need:** to know what they can do next, with the cost of each option stated.
- **Business Value:** this is the screen where the feature either preserves abstention or destroys it. Offered below the honest answer, it is an escalation the user performs. Offered anywhere else, or fired automatically, and the product loses the behaviour everything else is built to protect.
- *As someone who has just learned my own files do not answer this, I want to be shown what I could do instead, so that the honest "no" is a fork rather than a dead end.*

**Context / Background**
**Detailed Description:** `../ux/web-search.md` §2. The offer renders **below the abstention statement, never above it** — the abstention is the answer; this is what the user may do next. Three options, equal weight, each with its cost stated plainly:

| Option | Stated as |
| ------ | --------- |
| Search the web | sends your question out · this question only |
| Ask a larger model | uses credits · you have none |
| Add a source instead | keeps the answer in your own material |

**"Add a source instead" is listed deliberately.** It is the option that makes the next answer better permanently, and omitting it would make escalation look like the only way forward. It is the action M2-ABSTAIN-FE-055 already built; this ticket puts two siblings beside it.

The user may also escalate deliberately on a question their files *do* cover. That is fine — it is still one question, still one act — and the entry point for it is out of scope here, because it must never take the form of a composer control (`../ux/web-search.md` §1).

**Scope**
- The three options rendered below the abstention, at equal weight, each with its cost stated.
- Wiring "search the web" to the escalation, for that question only.
- Wiring "ask a larger model" to the online-AI path, disabled with its reason where credits do not exist.
- Keeping "add a source instead" as the existing add-source action.
- Keyboard reachability and a clear focus order that reaches the abstention text first.

**Out of Scope**
- **Any control in the composer.** There is no "search the web" toggle there and there must never be one (`../ux/web-search.md` §1).
- Any settings control that makes searching a default (M7-SET-FE-147 forbids it).
- The searching, answered and closed states (M6.5-WEB-FE-192).
- Suggested follow-ups, which belong to answered turns and not to this surface (M1-CONV-FE-180).

**Acceptance Criteria**
- **Acceptance Criteria:** An abstention renders exactly as it did before, and the three options render **beneath it**. Each option states its cost in the words the specification gives. Nothing on this surface is presented as the recommended or default action. Choosing "search the web" escalates that one question. **The escalation-not-fallback rule is preserved:** the offer is the only route to a search, it appears only after an abstention has been composed and rendered, and nothing on the screen is pre-selected, auto-focused for activation, or activated by the Enter key that submitted the question.
- **Edge Cases:** Credits are zero, which is the normal case before M8 — the larger-model option shows its cost as "you have none" rather than being hidden, because hiding it would misrepresent what the product can do. The provider is unavailable or unconfigured — the web option states that plainly rather than disappearing (`../ux/web-search.md` §4). A **partial** answer rather than a full abstention — the offer may render below the named gap, since that is the same situation; it never renders below a fully grounded answer. The user escalates twice on the same question — the second is a second act, authorised again. The window is below the breakpoint — the three options stack and none is dropped.
- **Permissions / Roles:** Single user — no roles. Not applicable.
- **UI States:** `../ux/web-search.md` §2 and §4 (Offered); `../ux/ask.md` §5 abstained — "the escalation offer renders below it, never above"; `../ux/ask.md` §6; `../states-and-edge-cases.md` §1.
- **Validation Rules:** **Nothing may render above the abstention statement.** No option may be default-activated. No control offering a search may exist anywhere except on this surface.
- **Audit / Logging Requirements:** Offering costs nothing and is not recorded. **Accepting is a decisions record** — the user authorised content to leave the machine, which is exactly the class of act the decisions store exists for (C6).
- **Analytics Events:** Local counter of offers made and offers accepted — the **escalation rate** named in `../web-search.md` §7. Nothing transmitted (C1).

**Real-World Example Scenarios**
- A user asks about a regulation they never added, reads that their files do not cover it, sees the three options, and chooses to add the regulation — which is the outcome the third option exists to make likely.
- A user asks the same question a week later, having still not added it, and escalates to the web. Nothing about the first refusal made the second one automatic.

**Dependencies & Assumptions**
- **Dependencies:** M2-ABSTAIN-FE-055, M6.5-WEB-BE-185, M6.5-WEB-SEC-187.
- **API / Data Touchpoints:** The abstention event; the escalation authorisation; the decisions store.
- **Assumptions:** M2-ABSTAIN-FE-055 placed the add-a-source action below the abstention statement in a region that can hold three options, as its scope requires. If it did not, the layout work belongs here and the estimate is low.

**Testing Notes / Scenarios**
- **Cold-start manual walkthrough:** Cold start with two documents indexed. Ask something they cover and confirm no offer appears anywhere — the offer belongs to abstention, not to every answer. Now ask something they plainly do not cover. Read the abstention first; confirm the three options are underneath it and that you had to read the honest answer to get to them. Read each option's cost. Press Enter without clicking anything and confirm nothing is sent. Click "add a source instead" and confirm you land in the add flow with the question retained. Come back, ask the uncovered question again, and this time choose "search the web".
- **Other scenarios:** With no provider configured, confirm the web option says so rather than vanishing. Tab through the surface and confirm focus reaches the abstention text before any option. Narrow the window and confirm all three options survive. Ask twenty uncovered questions in a row, decline every time, and confirm the proxy recorded no permitted request.
- **Known gaps:** Escalating on a question the corpus *does* cover has no entry point in v1 — deliberately, because every obvious place to put one is a composer control. Voice escalation is unspecified and deferred (`../web-search.md` §8). The larger-model option does nothing until M8.

**Effort & Granularity Check**
- **Estimate:** 3–4 hours · **Priority:** Critical
- **Labels / Component:** `phase:6`, frontend, `constraint:web-escalation`, `constraint:grounding`
- **Granularity:** Three options and their placement rule, on a surface that already exists.

### M6.5-WEB-SEC-187 — Per-question egress authorisation, opened and closed at the proxy

**Type:** Story

**User Story**
- **Actor:** someone who chose this product because nothing leaves their machine, and who has just knowingly let one question leave it.
- **User Need:** certainty that the door closed behind that question.
- **Business Value:** the proxy is what makes "per question" enforceable rather than an intention in application code (`../architecture.md` §5.1). Application-level enforcement is defeated by one dependency making an unexpected call, which is the realistic threat rather than malicious code.
- *As someone who let one question out, I want the permission to expire with that question, so that a single decision does not quietly become a standing one.*

**Context / Background**
**Detailed Description:** `../architecture.md` §5.1: two paths may be opened, both narrowly and both on request. Online AI authorises one destination for one conversation's traffic. **Web search authorises the search provider for one question, and it closes immediately afterwards.** Neither is sticky, and the proxy is the thing that guarantees it.

This ticket makes the authorisation a real, short-lived grant at the default-deny proxy built in M0-STACK-SEC-010, scoped to the search provider's destination and to one turn. When the turn ends — answered, abandoned, failed or stopped — the grant is gone. **A grant that outlives its turn is the defect this ticket exists to prevent**, and it is verified by reading the proxy, not by trusting the code that asked for it.

**Scope**
- A short-lived, destination-scoped grant at the proxy, opened by an accepted escalation.
- Closure of the grant when the turn ends, by every route a turn can end.
- A hard expiry so a grant cannot outlive its turn even if the closing path is missed.
- The refused-request counter continuing to distinguish refusals from permitted requests, and naming the destination (M7-SET-FE-147).
- Rejection of any request to a destination other than the provider's, even while a grant is open.

**Out of Scope**
- The online-AI authorisation, which is M8-ONLINE-SEC-169 and is per conversation rather than per question.
- Fetching, capping and using the content (M6.5-WEB-BE-188).
- The sandbox, which has no route to the proxy at all and is unaffected (C3).

**Acceptance Criteria**
- **Acceptance Criteria:** With no escalation accepted, the proxy permits nothing and the local-mode count stays a measured zero. Accepting an escalation opens a grant scoped to the provider's destination alone. A request to any other destination while the grant is open is refused and counted. When the turn ends by any route, the grant is closed. A grant left open by a missed code path expires on its own. **The escalation-not-fallback rule is preserved at the strongest available point:** since no grant exists unless a user accepted an offer, an automatic fetch is refused by the proxy even if application code attempts it — the constraint has a mechanism rather than a convention, which is what M7-SEC-TEST-166 requires before release.
- **Edge Cases:** The user stops generation mid-search — the grant closes with the turn, and any in-flight request is abandoned rather than completing after the turn is over. The turn fails with an error — the grant still closes; a failure path that leaks a grant is the worst version of this bug. Two escalations in quick succession — two grants, each scoped to its own turn, never one merged grant. The application asks for a grant with no user acceptance behind it — refused, and the attempt is recorded as an anomaly worth reading. The machine is offline — the grant opens and nothing can use it, which is correct; the surface says the web cannot be reached (M6.5-WEB-FE-192). A live database connection is configured — it is a separate permitted destination and its count stays separate, as M4-CONN-FE-096 already assumes.
- **Permissions / Roles:** Single user — no roles. Not applicable.
- **UI States:** Surfaced by `../ux/settings.md` §4 through M7-SET-FE-147 — as history, never as a control.
- **Validation Rules:** A grant is scoped to one destination and one turn. **No configuration, setting or preference may create a standing grant.** The count shown to the user comes from the proxy, never from the application.
- **Audit / Logging Requirements:** Opening and closing a grant are recorded with the turn, the destination and the timestamps, in the append-only store (C6). A refused request while a grant is open is recorded with its destination.
- **Analytics Events:** Local counters only — nothing transmitted (C1).

**Real-World Example Scenarios**
- A user escalates one question, gets an answer from the web, then asks four more questions. The proxy shows one permitted request and nothing since — which is the evidence the settings screen is showing them.
- A dependency attempts an update check during a turn that has a search grant open. It is refused, because the grant names the provider's destination and not the internet.

**Dependencies & Assumptions**
- **Dependencies:** M0-STACK-SEC-010, M0-STACK-SEC-011, M6.5-WEB-BE-185.
- **API / Data Touchpoints:** The proxy's grant mechanism and counters; the audit store.
- **Assumptions:** The proxy can express a grant narrow enough in both destination and time to be meaningful; if it cannot, that is a finding to raise rather than a reason to move enforcement into application code, which is the thing this design refuses.

**Testing Notes / Scenarios**
- **Cold-start manual walkthrough:** Cold start and use Askwell for a session without escalating anything. Open settings and confirm the permitted outbound count is zero and that the number comes from the proxy. Now ask an uncovered question and accept the web escalation. Watch the answer arrive. Return to settings and confirm exactly one permitted request, named with its destination. Ask a second question — any question — and confirm no further permitted requests appear. Restart Askwell and confirm the count is still one and no grant is open.
- **Other scenarios:** Accept an escalation and press stop while it is searching; then check the proxy for an open grant — there must be none. Force the turn to fail and check again. From inside a container, attempt a request to an unrelated host while a grant is open and confirm it is refused and counted. Attempt to open a grant from the application with no acceptance behind it and confirm refusal.
- **Known gaps:** The provider's destination is a fixture until M6.5-WEB-BLOCKED-195 is answered; the grant mechanism does not change when the real one arrives, but the destination list does. Online AI's per-conversation grant is separate and lands in M8.

**Effort & Granularity Check**
- **Estimate:** 4–6 hours · **Priority:** Critical
- **Labels / Component:** `phase:6`, security, `constraint:local-first`, `constraint:web-escalation`
- **Granularity:** One grant, its scope, and every route by which it must close. Upper bound because the closing paths are the work and missing one is the bug.

### M6.5-WEB-BE-188 — Fetch caps, delimitation, and never persisting web content

**Type:** Story

**User Story**
- **Actor:** someone whose escalated question has just pulled a page written by a stranger into the same prompt as their own contracts.
- **User Need:** that page treated as the most untrusted thing in the system, and gone when the turn is over.
- **Business Value:** C7 governs documents the user *chose*. A page written to contain instructions is not one of those, and web content is the most untrusted input Askwell handles (`../architecture.md` §5.2). If it were persisted into `chunks`, a hostile page could influence a future answer it was not part of.
- *As someone who has just let one question reach the open web, I want what came back to be treated as data and then discarded, so that one escalation cannot change how Askwell answers me next month.*

**Context / Background**
**Detailed Description:** `../web-search.md` §5. Fetched content is delimited exactly as document content is, and the system prompt's standing statement that retrieved content is data and never instruction is unchanged (C7). Fetches are **capped**: a small number of results, a size limit per page, and a timeout. A page that exceeds them is **dropped rather than truncated into the prompt** — truncation is how a size limit becomes a way of choosing which half of a hostile page gets in.

And the structural half: **fetched content is never chunked, never embedded, and never written into `chunks`.** It lives on the turn that fetched it and nowhere else.

**Scope**
- Fetching the passages behind the provider's results, within a capped count, size and time.
- Dropping any page that exceeds a cap, with the drop visible in the trace rather than silent.
- Delimiting fetched content identically to document content, in the versioned prompt files.
- Holding fetched content on the turn only — no chunking, no embedding, no write to `chunks`, no index of any kind.
- A test asserting that after an escalated turn, nothing new exists in the corpus.

**Out of Scope**
- Trace flagging of instruction-like patterns (M6.5-WEB-OBS-193).
- The provider call itself (M6.5-WEB-BE-185).
- Rendering (M6.5-WEB-FE-190).

**Acceptance Criteria**
- **Acceptance Criteria:** Fetches respect a capped result count, a per-page size limit and a timeout. A page over the size limit is **dropped, not truncated**, and the drop is recorded. Fetched content is delimited in the prompt exactly as document content is, and the standing statement is unchanged (C7). After an escalated turn completes, **the corpus is byte-for-byte unchanged**: no new chunk rows, no new embeddings, no new documents, nothing searchable. **The escalation-not-fallback rule is preserved:** because nothing fetched is ever indexed, a later question cannot retrieve web content from the corpus and so can never appear to have been answered from the user's files when it was not — and no future retrieval can be quietly improved by a past escalation.
- **Edge Cases:** A page that redirects repeatedly — capped and abandoned. A page that is not text at all — dropped rather than fed in as noise. A page that is exactly at the size limit — handled by one stated rule rather than by chance. All results dropped by the caps — the turn says nothing usable came back, which reads the same as nothing being found; it must not silently produce an uncited answer. A page containing text that looks like an instruction — delimited and used as data, exactly like a document (C7), and flagged in the trace (M6.5-WEB-OBS-193). The turn is stopped mid-fetch — in-flight fetches are abandoned and nothing is retained.
- **Permissions / Roles:** Single user — no roles. Not applicable.
- **UI States:** Consumed by `../ux/web-search.md` §3 and §4.
- **Validation Rules:** **Nothing fetched from the web may be written to `chunks` or embedded, under any circumstance.** A page exceeding a cap is dropped, never truncated. The delimitation of fetched content is identical to that of document content and the prompt's standing statement is never weakened.
- **Audit / Logging Requirements:** Each fetch is recorded with its URL, its outcome, and any cap that was hit. Drops are recorded with the reason.
- **Analytics Events:** Local counters of fetches and drops — nothing transmitted (C1).

**Real-World Example Scenarios**
- An escalated question pulls three pages; one is a 40 MB document dump and is dropped, and the answer says it used two sources rather than silently using a truncated third.
- A page carrying an injection attempt is used as data, the answer is unaffected, and a question asked three weeks later cannot retrieve that page because it was never stored.

**Dependencies & Assumptions**
- **Dependencies:** M6.5-WEB-BE-185, M6.5-WEB-SEC-187, M1-ASK-BE-037.
- **API / Data Touchpoints:** The prompt templates; the turn record. **Deliberately not** `chunks`, `documents` or the vector index.
- **Assumptions:** The caps are set conservatively at first and tuned with real use; they are configuration, not constants in code, and the current values are recorded so a change is a decision rather than a drift.

**Testing Notes / Scenarios**
- **Cold-start manual walkthrough:** Cold start with a small corpus. Note exactly what the library says it contains. Ask an uncovered question, escalate to the web, and read the answer. Return to the library and confirm it says exactly what it said before — no new source, no new document, no changed count. Ask a follow-up question with **no** escalation, phrased to invite the web content back, and confirm Askwell abstains rather than producing what it had a minute ago.
- **Other scenarios:** Point the fixture at an oversized page and confirm it is dropped rather than truncated, with the drop visible. Point it at a non-text resource. Configure every result to be dropped and confirm the turn says nothing usable came back rather than answering anyway. Stop a turn mid-fetch and confirm nothing was retained.
- **Known gaps:** Cap values are first guesses. The injection mitigation is exactly that — a mitigation, weaker here than for documents because the user chose their documents and did not choose these pages; that residual risk is documented rather than overclaimed.

**Effort & Granularity Check**
- **Estimate:** 3–4 hours · **Priority:** Critical
- **Labels / Component:** `phase:6`, backend, `constraint:injection`, `constraint:web-escalation`
- **Granularity:** Three caps and one prohibition. Small because the prohibition is the absence of work, and the test that proves it is short.

### M6.5-WEB-BE-189 — Retrieval timestamps, stored with the turn

**Type:** Story

**User Story**
- **Actor:** someone re-reading, a month later, an answer that came partly from the web.
- **User Need:** to know when the page was read, because it may not say the same thing now.
- **Business Value:** a document on disk does not change; a web page does. The date is what keeps the citation honest a month later, and without it a web citation quietly degrades into a claim with a broken link behind it.
- *As someone who keeps notes from months ago, I want each web citation to carry the date it was read, so that I know how much to trust it now.*

**Context / Background**
**Detailed Description:** `../web-search.md` §4 and `../ux/web-search.md` §3: **the retrieval timestamp is not a detail.** A page can change or vanish after the answer; a document on disk cannot. The date is what makes the citation honest later.

This ticket stores, with the turn, each web result's source domain, page title, full URL, the passage used, and the time it was retrieved — permanently and immutably, alongside the answer. Like the turn summary in M1-CONV-BE-177, these are **stored, never recomputed**: re-checking a URL later to refresh its date would replace what happened with what is happening.

**Scope**
- Web result records attached to the turn: domain, title, URL, passage, retrieval timestamp.
- Written in the same transaction as the answer they support.
- Immutable once written, and never refreshed or re-verified.
- Available to every surface that shows the turn — the answer, the collapsed turn, the trace, and export.

**Out of Scope**
- Rendering (M6.5-WEB-FE-190).
- Persisting the content into the corpus — forbidden (M6.5-WEB-BE-188).
- Re-checking whether a URL still resolves, at any time.

**Acceptance Criteria**
- **Acceptance Criteria:** Every web result used in an answer is stored with the turn carrying its domain, title, full URL, passage and retrieval time. **Type:** Story

**User Story**

- **Business Value:** an answer that blends the two is worse than either alone, because it makes the user's own material look like the web and the web look like their own material at the same time. The whole value of the provenance margin is that it is never wrong about this.
- *As someone reading an answer drawn from two very different kinds of source, I want each sentence to point at where it actually came from, so that I can trust the half I can check and be careful with the half I cannot.*

**Context / Background**
**Detailed Description:** `../ux/web-search.md` §3, "When an answer mixes both". Claims from the user's documents render normally with the margin. Claims from the web render in the separate region. **Each claim points at its own kind of source.** They are never blurred into one list, and **a web result never appears in the margin even when it supports the same point** — which is the case where the temptation is strongest and the erosion would be quietest.

`../web-search.md` §4 puts the same rule from the other direction: an answer may mix both, and when it does, each claim points at whichever kind of source it came from, never a blur of the two.

**Scope**
- Claim-level attribution to one kind of source, in an answer that uses both.
- Document claims keeping their leader and their margin card, exactly as before.
- Web claims pointing into the web region, in the web region's own visual language.
- Hover and keyboard pairing working within each kind, never across them.
- The rule that a web result supporting a documented claim still does not join the margin.

**Out of Scope**
- The web region itself (M6.5-WEB-FE-190).
- Conflict handling between a document and a web page — treated as it is between two documents (M2-PARTIAL-BE-059), not re-solved here.

**Acceptance Criteria**
- **Acceptance Criteria:** In an answer using both kinds, every factual claim carries a citation (C4) and each one resolves to exactly one kind of source. Document claims keep their leader and margin card. Web claims point into the web region. Hovering or focusing a claim raises only its own source, of its own kind. **A web result that supports a claim already grounded in a document does not enter the margin** — it stays in the web region, and the claim's document citation is unaffected. **The escalation-not-fallback rule is preserved:** a claim about the user's own material is never satisfied by a web source, and the mixed rendering makes any attempt to do so immediately visible rather than hidden in a blended list.

A web result contradicting a document — presented as a conflict with both citations and their dates, exactly as two documents would be (M2-PARTIAL-BE-059); Askwell does not silently prefer either, and does not prefer the web because it is newer. An answer that turns out to be entirely from documents after all — no web region renders, and the turn is an ordinary answer. An answer entirely from the web — no margin content, and the margin says so explicitly rather than being hidden (`../ux/ask.md` §2 — the margin is never hidden). Below the breakpoint — the reflowed inline cards and the web region remain visibly two different things.
- **Permissions / Roles:** Single user — no roles. Not applicable.
- **UI States:** `../ux/web-search.md` §3 (When an answer mixes both) and §4 (Mixed); `../ux/ask.md` §4 and §5; `../ux/design-system.md` §7.
- **Validation Rules:** No claim may cite both kinds through one shared representation. A web result may never be rendered in the margin, including when it supports the same point as a document.
- **Audit / Logging Requirements:** Citations record which kind of source each claim used, so the uncited-claim check (M1-CITE-TEST-045) can reconcile both kinds rather than treating a web-cited claim as uncited.
- **Analytics Events:** Local counter of mixed answers — nothing transmitted (C1).

**Real-World Example Scenarios**
- A user asks what their contract says about notice periods and what the current statutory minimum is. The first half cites their contract in the margin; the second half cites a government page with its date; neither is confused for the other.

**Dependencies & Assumptions**
- **Dependencies:** M6.5-WEB-FE-190, M1-CITE-BE-042, M1-CITE-FE-043, M2-PARTIAL-FE-058.
- **API / Data Touchpoints:** Citation records of both kinds; the answer composition path.
- **Assumptions:** Composition can attribute at claim level across two kinds of source as reliably as it already does across documents; if it cannot, the honest fallback is to keep the halves separate in the answer text rather than to guess an attribution.

**Testing Notes / Scenarios**

Ask the two-part question, watch it abstain on the half it cannot cover — or answer partially and name the gap — and escalate. Read the resulting answer and confirm the documented half has its margin cards and leaders, the web half has its own region with dates, and no card has moved between them. ### M6.5-WEB-FE-192 — The remaining states: searching, nothing found, unavailable, and the escalation closing

**Acceptance Criteria**

A search that cannot run says the web cannot be reached **while the abstention still stands as the answer** — failing to escalate is not failing to answer. After the turn, a closing note states that the search closed with this question and the next starts local again. - **Analytics Events:** Local counters of escalations by outcome — the escalation rate from `../web-search.md` §7. Nothing transmitted (C1).

**Real-World Example Scenarios**

- A user escalates, gets a web answer, asks a follow-up, and sees nothing from the web in it — because the next question started local, exactly as the closing note said.

**Dependencies & Assumptions**
- **Dependencies:** M6.5-WEB-FE-186, M6.5-WEB-FE-190, M6.5-WEB-SEC-187, M1-CONV-FE-178.
- **API / Data Touchpoints:** The escalation outcome; the stored turn and its summary.
- **Assumptions:** Named progress can be produced for a search as it is for retrieval; if the provider gives no intermediate signal, the labels describe the stage rather than inventing granularity.

**Testing Notes / Scenarios**
- **Cold-start manual walkthrough:** Cold start. Ask an uncovered question, accept the escalation, and read the progress — confirm it says the question has gone out rather than showing a bare spinner. Read the answer, then read the closing note. Ask a second question and confirm it is answered locally with nothing from the web. **Acceptance Criteria**
- **Acceptance Criteria:** Ten tasks run three times each with the network disconnected. Every response abstains and offers the escalation; **none searches**. The proxy reports zero permitted outbound requests across all runs. The category is reported as pass or fail, never as a mean — "0.97 on ten tasks" is a failure that reads as fine. Deliberately introducing an automatic fetch on thin retrieval **fails the suite**, which is the check that the suite works. The gate's total is 165 tasks across eight categories. **The escalation-not-fallback rule is preserved by making it measurable:** this suite is the enforcement point C10 is verified at, and `../AGENTS.md` C5's standing rule applies — **do not weaken these tests to make a change pass, and do not lower the retrieval threshold to improve the number.**
- **Edge Cases:** A task where the model happens to abstain for the wrong reason — the assertion is about the search not happening, so it still passes, and the abstention subset is what tests the abstention itself. A run where the fixture provider is misconfigured to be reachable — the proxy assertion still holds, because no grant was opened. A task that errors for infrastructure reasons — recorded as an infrastructure failure, distinct from a discipline failure; the two must never be conflated, because one is a broken runner and the other is a broken product. - **Audit / Logging Requirements:** Runs recorded with model, prompt version, threshold and date, as every suite is.
